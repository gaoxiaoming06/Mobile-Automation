# 自动化测试平台需求

## 背景

当前需求是建设一个新的自动化测试平台，核心目标是把连接到本机或测试机集群的 Android / iOS 设备、被测应用包、测试流程和测试报告统一接入可视化面板。MVP 首版以 Android 设备闭环为主，同时已经开始接入 iOS 基础能力：设备发现、截图预览、电量采样，以及配置 WebDriverAgent 后的基础远程操作。测试人员不需要直接操作命令行工具，即可在浏览器中查看设备画面、操控设备、录制操作路径、编辑步骤、重复执行测试，并获得包含性能和异常信息的 HTML 测试报告。

该平台当前主要项目目标命名为 `PageStateFlow`：页面状态资产驱动的移动端智能回放测试平台。产品主线面向“应用包 + 设备 + 页面状态资产库 + 语义执行 + 结构化回放 + 性能基线 + 报告通知”的自动化测试场景。操作录制和自动回放不再是裸坐标脚本，也不再默认要求穷尽全 App 的全局业务图谱；平台应把每个稳定页面 / 页面变体保存为可识别、可操作、可验证的 PageModel，把页面上的可操作区域保存为 PageElement，把页面之间的动作结果保存为 PageTransition，把到达目标页后的表单填写、选择器、提交和局部验证保存为 PageTask。StructuredFlow 继续存在，但定位调整为基于页面资产生成或录制固化的一条线性路径快照，用于回归、复现、执行到中间状态和 AI/CI 调用。后续还需要支持页面资产库、动态预期覆盖、新包冒烟、指定页面 / 指定流程验证、版本性能对比、定时巡检、CI / AI 触发和测试结果通知。

## 目标用户与角色

| 角色 | 目标 | 典型行为 |
|---|---|---|
| 测试人员 | 快速录制和执行自动化测试 | 连接设备、录制路径、编辑步骤、重复执行、查看报告 |
| 开发人员 | 复现问题和定位崩溃 / ANR | 选择设备、回放问题路径、查看日志和性能证据 |
| 测试负责人 | 查看执行结果和稳定性趋势 | 管理用例、查看报告、对比多次执行结果 |
| 自动化维护者 | 扩展平台能力 | 新增动作类型、接入更多设备能力、维护驱动层 |
| 构建 / CI 负责人 | 新包出来后自动发起冒烟 | 配置包来源、触发策略、质量门禁、通知回调 |
| 质量负责人 | 观察包质量和性能趋势 | 查看不同版本包的冒烟结果、性能劣化和稳定性趋势 |

## 平台范围

| 能力 / 场景 | Android MVP | iOS | 是否要求一致 | 备注 |
|---|---|---|---|---|
| 设备发现与状态展示 | 是 | 基础支持 | 是 | Android 基于 ADB；iOS 基于 libimobiledevice + xcrun |
| 实时画面预览 | 是 | 基础支持 | 是 | Android 浏览器内 scrcpy；iOS 先使用 idevicescreenshot 截图轮询 |
| 远程点击 / 滑动 / 返回 | 是 | 部分支持 | 尽量一致 | iOS 点击/长按/滑动/Home/输入依赖 WDA；Back 无通用系统能力 |
| 文本输入 | 是 | WDA 支持 | 是 | iOS 需要配置 WDA |
| 操作录制 | 是 | 部分支持 | 是 | iOS 在可控制能力开启后复用统一 Step 模型 |
| 自动回放 | 是 | 部分支持 | 是 | iOS 在 WDA 可用时按同一 Runner 回放 |
| 性能采集 | 是 | 基础支持 | 指标尽量一致 | iOS 当前采集电量，CPU/内存/FPS 后续扩展 |
| 崩溃 / ANR 捕获 | 是 | 待支持 | 部分一致 | iOS crash/hang 日志后续接入 |
| 报告生成 | 是 | 基础支持 | 是 | iOS 执行复用 Web 报告详情与 HTML 导出 |
| 应用包管理 | Android APK 优先 | IPA 后续支持 | 部分一致 | SMB / 上传 / CI Webhook 均登记为 AppVersion |
| 冒烟套件 | 是 | WDA 可用后逐步支持 | 是 | 用例级 shuffle / sampling，不默认打乱单个用例内部步骤 |
| OCR / 截图断言 | Android 优先 | 后续支持 | 尽量一致 | OCR 首选本地引擎；截图基准图必须人工确认 |
| 版本性能对比 | 是 | 基础指标后支持 | 是 | 当前阶段并排展示、人工判断，不自动阻断 |
| 企业微信通知 | 是 | 是 | 是 | 以执行任务和套件配置为准 |

## 使用场景

### 场景 1：测试人员录制并执行一次回归流程

1. 用户打开 Web 面板。
2. 面板显示当前连接的 Android 设备和可发现的 iOS 设备，并标记每台设备的可用能力。
3. 用户选择一台设备，进入设备预览页。
4. 用户在预览页上点击“开始录制”。
5. 用户通过预览页完成点击、输入、滑动、返回等操作。
6. 面板按顺序生成可视化步骤。
7. 用户停止录制，编辑步骤参数。
8. 用户点击“执行一次”。
9. 平台按步骤回放，并生成执行报告。

### 场景 2：测试人员做稳定性轮询

1. 用户选择一个已录制用例。
2. 用户选择目标设备或设备组。
3. 用户配置执行模式为“循环执行”或“执行 N 次”。
4. 用户配置每轮间隔、失败后是否继续、最大执行时长。
5. 平台持续执行测试，采集性能、异常和步骤结果。
6. 执行结束后生成聚合报告，展示每轮结果和失败位置。

### 场景 3：开发人员复现崩溃问题

1. 开发人员打开已有测试报告。
2. 查看崩溃发生前的步骤、截图、设备信息、日志和性能曲线。
3. 在同型号设备上重新执行对应用例。
4. 若复现成功，平台记录新的崩溃证据并附加到报告。

### 场景 4：维护者编辑已有录制路径

1. 用户打开测试用例详情。
2. 用户删除无效步骤，插入等待步骤或断言步骤。
3. 用户调整某一步的坐标、滑动方向、输入文本、超时时间。
4. 用户保存新版本，并执行验证。

### 场景 5：新包冒烟验证

1. CI/CD 打包完成后通过 Webhook 把构建信息推送到平台，或平台从 SMB 目录扫描到新包。
2. 平台解析包信息，记录版本；一次构建建议由 `versionName + buildNumber + commitId + branch` 唯一标识。
3. 平台按 App、分支过滤条件和触发规则自动选择冒烟套件和目标设备。
4. 平台把包安装到指定设备或设备组，并校验设备上目标 App 版本。
5. 平台执行安装检查、启动检查、固定关键流程、轻量性能采样和异常监听。
6. 执行期间监听崩溃、ANR、卡顿、命令失败和设备断连。
7. 执行结束后向企业微信推送结果通知，附带 HTML 报告链接。

### 场景 6：指定流程与期望结果验证

1. 用户创建或导入一条测试流程。
2. 用户为流程添加结构化断言，例如 `assert_text`、`assert_image`、App 存活、无 crash、性能指标低于阈值。
3. `assert_text` 使用 OCR 识别屏幕指定区域文字，判断是否包含、等于或不包含预期文本。
4. `assert_image` 截取指定屏幕区域，与人工审核过的基准图按相似度阈值对比。
5. 含 `assert_image` 的流程第一次执行时，平台只保存“待审基准图”，不自动设为正式基准。
6. 用户在报告中确认基准图后，后续执行才进行正式对比。
7. 用户选择目标包和目标设备执行。
8. 平台按动作步骤和断言步骤执行，并将每个断言的结果写入报告。
9. 失败断言在报告中展示实际截图、基准图、差异图、OCR 结果或相关日志。
10. 若用户只输入自然语言期望结果，平台应优先通过规则模板解析成候选断言；无法解析时只作为备注保存并提示用户手动选择断言类型，不应直接作为机器判定依据。

### 场景 7：性能基线对比

1. 用户选择某个包和测试计划执行性能测试。
2. 平台按设备、流程和包版本记录关键性能指标。
3. 报告详情页提供“与历史版本对比”入口。
4. 用户选择基线版本；默认可推荐同设备、同套件、最近一次通过的版本。
5. 平台并排展示启动耗时、关键流程耗时、CPU、内存、FPS、卡顿、crash/ANR 数量等指标。
6. 包版本列表页支持选中两个版本后进入同一对比视图。
7. 当前阶段不做自动劣化判定、不自动阻断流程，只展示数据供人工判断；阈值告警作为后续可选能力。

### 场景 8：步骤级预期输入与验证

1. 用户录制或编辑一条固定业务流程。
2. 用户为每一步补充“这一步执行完应该发生什么”，例如出现某段文字、进入某个页面、某个按钮可见、屏幕发生变化、App 仍然存活、无 crash / ANR、某个指标不超过阈值。
3. 录制过程中平台自动采集每一步执行前 / 后的状态证据，并按可靠性生成候选预期，减少用户逐步手动添加的成本。
4. 平台默认启用高可靠预期，例如无 crash / ANR、App 可响应；中可靠预期例如屏幕变化、OCR 新增关键文字、截图区域相似度应作为候选或建议项，允许用户确认、删除或调整。
5. 平台通过结构化表单、常用模板、自动候选预期或从截图中选择区域的方式，让用户把预期结果保存为可执行验证条件。
6. 若用户输入自然语言预期，例如“点击登录后应该看到首页”，平台先用规则模板生成候选验证条件，用户确认后才保存；无法解析的内容只作为备注。
7. 回放时，Runner 每执行一步，都按该步骤配置的预期结果进行验证。
8. 验证通过时，步骤结果为 passed，并记录实际证据。
9. 验证失败时，步骤结果为 failed，报告展示预期、实际、截图、日志、OCR 结果、图像差异或指标数据。
10. 对滑动、等待、点击这类容易受当前状态影响的步骤，平台可以额外使用状态锚点和语义动作辅助执行，但它们只是确保步骤走到正确状态的机制，不是唯一验证方式。

### 场景 9：录制步骤语义化定位与修复

1. 用户进入用例录制页并选择目标设备。
2. 用户在预览画面中点击某个按钮或文字区域。
3. 平台仍记录坐标作为 fallback，同时采集点击点附近的截图、设备分辨率、目标 App 信息和可用 UI 层级 / OCR 信息。
4. Android first 阶段，平台通过 UIAutomator dump 查找点击点所在控件，生成元素定位候选，例如 resource-id、content-desc、text、class 和 bounds。
5. 如果控件候选不稳定或不可用，平台使用 OCR 在点击点附近生成文字目标候选。
6. 如果文字目标也不可用，用户可以从截图中圈选区域，生成图像或区域目标候选。
7. 用户在步骤编辑器里看到“坐标点击、元素点击、文字点击、图像 / 区域点击”的候选，并选择是否转换。
8. 用户插入“看到文字则点击，否则跳过”的条件分支，用于处理可能出现的弹窗或权限提示。
9. 回放时，Runner 优先按已确认的语义目标寻找并执行；找不到目标时按步骤失败策略使用坐标 fallback、重试、跳过或失败。
10. 回放失败后，报告展示目标定位失败原因和截图证据，用户可以基于失败截图修复该步骤目标，而不是必须重新录制整条用例。

### 场景 10：源码扫描生成候选业务图谱

1. 自动化维护者在平台中登记一个 App，并配置其源码目录、平台类型和包名 / bundle id。
2. 平台只读扫描源码，不要求业务 App 新增自动化契约或修改代码。
3. Android first 阶段，平台扫描 AndroidManifest、Activity、Fragment、Navigation XML、Compose NavHost、Router / DeepLink、layout XML、strings、onClick、navigate、startActivity 等信息。
4. 平台生成候选业务节点，例如登录页、首页、班级页、发布作业页。
5. 平台为每个候选节点生成状态识别 matcher，例如 activity、route、resource-id、文本、content-desc、截图区域。
6. 平台生成候选操作边，例如首页进入班级页、班级页进入发布作业页。
7. 自动化维护者在 Dashboard 中查看候选节点 / 边，执行合并、重命名、废弃、补充预期和确认。
8. 平台把确认后的资产保存为 active 图谱版本，未确认内容保留为 draft。

### 场景 11：选择目标节点并自动规划执行路径

1. 用户选择目标 App、包版本、设备和目标节点，例如“新建作业页面”。
2. 平台识别当前设备所处业务节点；如果未知，则按起始策略启动、重启或安装后启动目标 App。
3. 平台从当前节点或根节点规划到目标节点的路径。
4. 平台展示规划路径，包括将要经过的节点、边、前置条件、动作策略和后置预期。
5. 用户确认后执行。
6. Runner 按路径逐边执行：检查前置条件、处理阻塞弹窗、选择动作策略、执行动作、采集截图 / 日志 / 性能、验证状态迁移和后置预期。
7. 若执行偏离路径，Runner 按策略恢复、重试、回到根节点、重新规划或失败。
8. 执行结束后，报告展示规划路径、实际路径、失败节点 / 边、expected / actual、截图、视频时间点、日志和性能数据。

### 场景 12：无源码 App 通过探索和录制沉淀图谱

1. 用户登记一个无源码 App 或未配置源码目录的 App。
2. 用户可以通过手工录制、自动探索或手工维护创建候选节点和候选边。
3. 平台在录制或探索过程中采集截图、UI 树、OCR 文本、activity / bundle 状态和操作结果。
4. 平台根据操作前后状态生成候选节点 / 边 / matcher / action strategy / expectation。
5. 手工录制不应长期保存为一条孤立线性脚本；录制每一步应展示“执行前节点识别规则、边的动作策略、执行后目标节点规则和后置预期”，用户确认后直接进入 App 级业务图谱候选库。
6. 录制确认入口必须支持三类变更：新增节点、新增边、修复已有边动作策略 / 预期；用户可以把高置信候选直接晋级为 active，也可以保留为 draft 等待多次验证。
7. 候选资产默认是 draft，不直接进入 active 图谱；但当满足自动晋级策略（多次观测稳定、critical matcher 命中、边执行通过、无 crash / ANR）时，可以自动转正。
8. 自动化维护者确认、合并、重命名或废弃候选资产。
9. 确认后的图谱可以和有源码 App 一样进行目标节点执行。

### 场景 13：AI / CI 动态预期覆盖验证

1. AI Agent 或 CI 构建系统完成代码修改和打包。
2. AI / CI 通过 API、CLI 或 MCP adapter 调用平台，传入 App、包、设备、目标节点和本次动态预期。
3. 示例：AI 修改了“新建作业页面”文案，从 `xxx` 变成 `yyy`，调用平台验证目标节点 `homework.create_page`，并传入 `text_visible: yyy`。
4. 平台安装或启动目标包，按 active 业务图谱规划路径到目标节点。
5. 沿途每一步继续执行默认保障：无 crash、无 ANR、App 可响应、状态迁移正确；可选执行性能基线对比。
6. 到达目标节点后，平台应用本次 RuntimeOverlay 动态预期，验证新文案、新布局、新按钮行为或新性能阈值。
7. 动态预期只作用于本次 Run，不自动写入 active 图谱。
8. 平台返回结构化结果、失败原因、actual 信息、报告链接、截图、视频和日志，供 AI / CI 继续修复或阻断流程。

### 场景 14：资产驱动巡检

1. 用户选择目标 App、设备、页面资产范围和巡检策略，例如“从当前页面开始巡检”“只巡检主页周边”“巡检所有关键路径页面”。
2. 平台先采集当前 Observation，并匹配到已保存 PageModel；如果当前页面未知或置信不足，不进入巡检执行，而是提示补录页面资产或转入稳定性探索。
3. 平台读取当前 PageModel 的页面区域、PageElement、PageTransition 和 PageTask，生成一轮受控巡检计划。
4. 对当前页面，平台先执行低风险页面健康动作，例如在人工标注的内容区上下滑动、检查标题栏 / 底部导航 / 固定区域是否仍可识别、验证关键 PageElement 是否能重定位。
5. 对已确认的 PageTransition，平台按风险和优先级逐条执行，验证目标页面是否可达、页面 matcher 是否稳定、动作耗时是否异常、是否出现 crash / ANR / 黑屏 / 弹窗阻断。
6. 巡检过程中不得盲目点击所有 OCR 文本；未录入为正式 PageElement / PageAbility 的候选只进入建议，不直接执行高风险动作。
7. 巡检结果生成报告，展示页面覆盖率、元素定位成功率、边稳定性、路径缺口、性能耗时、异常事件和建议修复入口。
8. 若发现新页面、新元素或疑似新边，平台只生成候选进入候选管理 / 资产录制确认流程，不直接写入 active 页面资产库。

## 功能需求

### REQ-001：可视化面板基础框架

平台必须提供一个 Web 可视化面板，用于承载设备管理、设备预览、操作录制、步骤编辑、测试执行和报告查看能力。

最低要求：

- 支持设备列表页、设备详情 / 预览页、用例管理页、执行记录页、报告详情页。
- 支持实时状态刷新，不要求用户手动刷新页面才能看到设备状态和执行进度。
- 面板应区分空状态、加载中、正常、失败、断连等状态。
- 面板应提供清晰的主导航，便于在设备、用例、报告之间切换。

### REQ-002：设备发现与设备管理

平台必须自动发现当前可连接的 Android 和 iOS 设备，并在面板中展示。

设备列表至少包含：

- 设备 ID / UDID。
- 平台类型：Android 或 iOS。
- 连接状态：在线、离线、占用中、执行中、异常。
- 设备型号、系统版本、屏幕尺寸、分辨率。
- 当前预览状态、当前执行状态。
- 可用能力，例如预览、点击、滑动、输入、性能采集、崩溃采集。

设备管理要求：

- 设备发现应自动进行：平台启动后立即扫描设备，并周期性刷新设备状态。
- 支持手动刷新设备列表，作为立即重扫、故障恢复和调试入口，而不是日常发现设备的唯一方式。
- 支持设备断连后状态自动更新。
- 支持设备重新连接后恢复可用状态。
- 同一设备同一时间只能被一个执行任务独占控制，除非后续明确支持多人共享。

### REQ-003：设备选择与实时预览

用户选择某台设备后，平台必须显示该设备当前界面预览。

预览要求：

- 预览画面应能持续更新，用户可以看到设备当前界面变化。
- 预览区域应保留设备宽高比。
- 支持竖屏、横屏和旋转后的显示。
- 支持画面缩放或自适应容器。
- 预览断开时需要提示原因，并允许用户重试。
- 预览区域应标记当前设备平台、分辨率、缩放比例和连接状态。

### REQ-004：预览页远程操控

用户必须可以直接在预览页上操控选中的设备。

基础操作包括：

- 点击。
- 长按。
- 滑动 / 拖拽。
- 返回。
- Home。
- 最近任务，Android 支持，iOS 当前不暴露。
- 文本输入。
- 清空输入。
- 唤醒 / 锁屏，若设备和平台支持。
- 截图。

交互要求：

- 用户在预览区域点击时，平台应将浏览器坐标转换为设备真实坐标。
- 滑动操作应记录起点、终点、方向、距离和持续时间。
- 横竖屏或缩放变化后，坐标转换仍应正确。
- 操作失败时应在 UI 中展示失败原因。

### REQ-005：操作录制生命周期

平台必须支持录制用户在预览页上的操作路径。

录制生命周期包括：

- 开始录制。
- 暂停录制。
- 继续录制。
- 停止录制。
- 放弃录制。
- 保存为测试用例。

录制要求：

- 开始录制后，用户在面板中触发的设备操作必须按顺序生成步骤。
- 每一步应记录操作类型、参数、发生时间、相对上一步的间隔、执行前截图或缩略图。
- 每一步应记录坐标空间和回放上下文，包括设备分辨率、预览渲染区域、屏幕方向、坐标比例、录制来源和目标 App。
- 滑动 / 拖拽类动作应保留起点、终点、持续时间和必要的路径采样点，便于复现长路径操作。
- 录制会话应保存会话级元数据，例如目标设备、平台、App、录制开始时间、总时长、分辨率、方向和录制工具版本。
- 录制期间应展示当前已录制步骤数量。
- 录制期间应允许用户添加备注。
- 录制停止后必须进入步骤编辑或保存流程。

### REQ-006：步骤可视化与编辑

平台必须把录制路径展示为可编辑的步骤列表。

每一步至少展示：

- 步骤序号。
- 动作类型。
- 关键参数摘要，例如坐标、文本、滑动方向。
- 类型图标、类型颜色或其他稳定视觉标识，用于快速区分点击、滑动、输入、等待、断言等步骤。
- 相对上一步延迟、步骤发生时间或最近一次执行耗时。
- 执行前 / 后截图缩略图，至少支持执行前截图。
- 期望等待时间或自动计算延迟。
- 启用 / 禁用状态。
- 最近一次执行结果。

编辑能力包括：

- 删除步骤。
- 插入步骤。
- 复制步骤。
- 拖拽排序。
- 修改步骤参数。
- 启用或禁用步骤。
- 为步骤添加备注。
- 设置步骤失败后的处理方式。

### REQ-007：动作类型覆盖

平台必须支持基础动作类型，并为后续扩展保留模型。

MVP 建议动作：

| 动作类型 | 说明 | Android | iOS |
|---|---|---|---|
| tap | 点击坐标 | 必须支持 | 必须支持 |
| long_press | 长按坐标 | 必须支持 | 必须支持 |
| swipe | 滑动 | 必须支持 | 必须支持 |
| back | 返回 | 必须支持 | 需映射 |
| home | 回到系统首页 | 必须支持 | 需确认 |
| recent_apps | 最近任务 / 应用切换 | 必须支持 | 暂不支持 |
| input_text | 输入文本 | 必须支持 | 必须支持 |
| clear_text | 清空输入 | 建议支持 | 建议支持 |
| wait | 等待固定时间 | 必须支持 | 必须支持 |
| screenshot | 截图 | 必须支持 | 必须支持 |
| launch_app | 启动目标 App | 建议支持 | 建议支持 |
| close_app | 关闭目标 App | 建议支持 | 建议支持 |
| wait_until_visible | 等待目标文字 / 图像 / 状态出现 | 后续支持 | 后续支持 |
| tap_on_text | 基于 OCR 文本点击 | 后续支持 | 后续支持 |
| tap_on_image | 基于图像锚点 / 人工区域点击 | 支持人工区域中心点击；图像相似检索后续支持 | 后续支持 |
| scroll_until_visible | 滑动直到目标可见 | 后续支持 | 后续支持 |
| assert_image | 图像断言 | 可后续支持 | 可后续支持 |
| assert_text | 文本 / OCR 断言 | 可后续支持 | 可后续支持 |

说明：

- `screenshot` 既可以作为用户录制的显式步骤，也可以作为 Runner 自动采集证据的内部动作。
- 回放执行时，Runner 必须在每个步骤完成后自动截图，并将截图关联到该步骤执行结果；该自动截图不要求写入用户可编辑的步骤列表。
- 若步骤执行失败、超时或触发异常，Runner 还应保留失败现场截图和必要日志。

### REQ-008：测试用例管理

录制完成后，平台必须能将步骤保存为测试用例。

用例信息包括：

- 用例名称。
- 用例描述。
- 所属 App / 产品模块 / 测试套件，若尚未接入包管理则至少保留目标 App 信息。
- 目标平台：Android、iOS 或双端。
- 目标 App 信息：Android package name / iOS bundle id。
- 关联设备要求，例如系统版本、屏幕方向、分辨率要求。
- 步骤列表。
- 用例版本。
- 创建人、创建时间、更新时间，若实现账号体系。
- 标签，例如冒烟、回归、稳定性、问题复现。

用例能力包括：

- 新建。
- 查看。
- 编辑。
- 删除。
- 复制。
- 导入 / 导出，建议支持 JSON。
- 版本记录，至少保留最近修改时间和修改说明。

用例归属原则：

- 测试用例是 App / 业务流程 / 测试套件级资产，不应强绑定到单台设备。
- 设备是执行资源；执行前根据用例的平台、能力和设备要求筛选可运行设备。
- 设备管理页可以提供“可在当前设备执行”的快捷入口，但完整用例列表、编辑、复制、导入导出应归属于用例库 / 用例管理模块。

结构化后的用例语义：

- 平台核心入口从“选择一条固定坐标脚本并回放”升级为“选择一条结构化录制用例并按状态、语义动作和预期执行”。
- v2 中的“用例”不应等同于裸坐标脚本；它表示一个有限范围的 Smart Recorded Flow，包含目标 App、包版本、起点、终点、角色 / 账号、起始策略、步骤 beforeState、语义动作、afterExpectations 和质量门禁。
- 每次执行时平台必须基于当前 Observation、用例快照、设备状态和 RuntimeOverlay 执行该 Flow，并把本次 FlowSnapshot 保存到报告中，作为该次运行的可追溯证据。
- 用例库长期保留为产品主入口；目标节点测试、源码扫描、候选图谱治理保留为高级 / 辅助能力，用于补充结构化用例的状态锚点、动作候选和预期候选。
- 手工录制模块长期定位是“结构化用例录入器”：用户每操作一步，平台生成 beforeState、ActionPolicy、afterExpectations 和证据，保存后进入用例库并可复用执行。

### REQ-009：自动回放与执行模式

平台必须支持按步骤自动控制设备完成测试执行。

执行模式包括：

- 执行一次。
- 执行 N 次。
- 持续循环执行，直到用户停止。
- 按最大时长执行，达到时长后停止。

执行配置包括：

- 执行设备或设备组。
- 执行次数。
- 每轮间隔。
- 步骤间默认间隔。
- 单步超时时间。
- 失败后停止或继续。
- 是否执行前重启 App。
- 是否执行前清理 App 数据，Android / iOS 能力需分别确认。
- 是否执行前截图。
- 是否每步执行后截图，MVP 默认开启。
- 是否执行失败时截图和采集日志。
- 是否执行期间录制设备视频，MVP 默认开启。

### REQ-010：执行过程控制

测试执行过程中，用户必须能看到实时进度并进行控制。

过程控制包括：

- 开始执行。
- 暂停执行。
- 继续执行。
- 停止执行。
- 强制结束。
- 查看当前执行到第几轮、第几步。
- 查看当前步骤状态。
- 查看最近日志和异常提示。

执行状态至少包括：

- pending。
- running。
- paused。
- passed。
- failed。
- stopped。
- timeout。
- device_lost。

### REQ-011：性能数据采集

测试执行过程中，平台必须记录设备性能数据，用于报告分析。

建议采集指标：

- CPU 使用率。
- 内存占用。
- FPS / 帧率，若可采集。
- 网络收发流量。
- 电量。
- 温度，若设备支持。
- 磁盘 / 存储占用，若可采集。
- 目标 App 进程状态。

采集要求：

- 指标需要按时间线记录。
- 指标应关联到执行轮次和步骤。
- 支持配置采样间隔。
- 报告中应展示关键指标最大值、平均值、趋势和异常点。
- Android 与 iOS 指标不可完全一致时，报告需明确标记缺失原因。

### REQ-012：崩溃、ANR 与异常采集

平台必须在测试执行过程中捕获异常并写入报告。

异常类型包括：

- Android crash。
- Android ANR。
- iOS crash。
- iOS hang / watchdog，若可采集。
- 设备断连。
- 预览断流。
- 操作执行失败。
- 目标 App 未启动或进程退出。
- 测试步骤超时。

异常证据至少包括：

- 异常发生时间。
- 所属设备。
- 所属用例、轮次、步骤。
- 异常摘要。
- 相关日志。
- 发生时截图。
- 若可获取，包含堆栈、进程、线程、系统日志。

### REQ-013：测试报告生成

每次测试执行结束后，平台必须生成测试报告。

报告内容包括：

- 执行摘要：用例、设备、平台、开始时间、结束时间、耗时。
- 执行结果：通过、失败、停止、超时、设备断连。
- 执行配置：次数、循环模式、采样间隔、失败策略。
- 每轮结果。
- 每一步结果和耗时。
- 步骤截图或关键截图。
- 性能数据趋势图。
- 崩溃、ANR、异常列表。
- 附件列表，例如日志、截图、执行视频、原始指标 JSON。

报告形式建议：

- Web 报告详情页必须支持。
- HTML 导出必须支持。
- JSON 原始结果建议保留为内部数据或后续 API 导出，方便 CI 和问题追踪。
- PDF 导出首版不支持。

### REQ-014：执行记录与证据留存

平台必须保存测试执行记录和必要证据，便于回溯。

留存内容包括：

- 测试用例快照。
- 执行配置快照。
- 步骤执行结果。
- 性能采样数据。
- 崩溃 / ANR / 异常日志。
- 截图。
- 设备录屏视频。
- 设备信息。

留存要求：

- 报告应引用执行时的用例快照，而不是只引用最新用例。
- 原始数据应可用于重新生成报告。
- 回放执行时，每个步骤完成后必须自动生成步骤后截图，并关联到 `StepResult`。
- 步骤失败、超时、设备断连、Crash、ANR 时，必须保留失败现场截图和相关日志。
- 测试执行期间默认启动设备录屏，录制对象为当前执行设备的屏幕画面。
- Run 状态为 passed、failed、timeout、device_lost、stopped 时，若设备和工具链支持录制，均应保留本次执行视频并作为报告附件。
- 视频是测试结果证据的一部分，不再提供“通过后删除 / 通过也保留”的执行级选项。
- 若平台因设备、系统限制或工具异常无法录制视频，报告必须展示 `video_unavailable` 或明确失败原因，不能静默缺失。
- 应提供清理策略，避免截图、日志、视频和报告无限增长。

### REQ-015：跨平台能力抽象

平台必须抽象 Android 与 iOS 设备控制能力，避免业务层直接依赖某个平台命令。

要求：

- Web 面板和测试执行器使用统一动作模型。
- Android / iOS Driver 各自实现设备发现、预览、控制、性能采集和异常采集。
- 当某个平台不支持某个动作时，UI 和执行报告必须明确提示。
- 同一个测试用例可以声明支持平台，执行前校验目标设备是否满足能力要求。

### REQ-016：坐标、分辨率、缩放与方向适配

平台必须处理预览画面和真实设备坐标之间的转换。

要求：

- 记录原始设备分辨率。
- 记录预览容器大小和缩放比例。
- 点击 / 滑动必须转换为设备真实坐标。
- 录制步骤应支持相对坐标或归一化坐标，降低不同分辨率回放失败概率。
- 横竖屏变化后应刷新坐标映射。
- 报告中应能展示步骤坐标和当时截图，便于排查错误。

### REQ-017：目标 App 管理

平台应支持围绕目标 App 执行测试。

建议能力：

- 配置 Android package name。
- 配置 iOS bundle id。
- 启动 App。
- 关闭 App。
- 重启 App。
- 获取 App 进程状态。
- 获取 App 版本信息。
- Android 支持安装 APK，iOS 是否支持安装 IPA 待确认。
- 执行前可选择是否清理数据，具体能力按平台区分。

### REQ-018：多设备与并发执行

平台应支持多设备管理，并为并发执行留出能力。

要求：

- 设备列表可同时展示多台设备。
- 单个执行任务可选择一台设备。
- 后续应支持同一用例在多台设备上并发执行。
- 设备被任务占用时，其他用户或任务不能抢占，除非具备管理员强制释放能力。
- 并发执行报告应能按设备分组展示。

### REQ-019：实时执行观察

平台应在执行过程中提供实时反馈，而不是只在结束后展示报告。

实时反馈包括：

- 当前轮次。
- 当前步骤。
- 当前设备截图或预览。
- 最近步骤结果。
- 当前性能指标摘要。
- 异常提示。
- 执行日志流。

### REQ-020：导入、导出与集成

平台应支持后续接入 CI、外部工具和测试资产管理流程。

建议能力：

- 测试用例 JSON 导入 / 导出。
- 执行结果 JSON 导出。
- 报告 HTML 导出。
- 提供 REST API 或 CLI 触发执行。
- 支持在 CI 中指定用例、设备、执行次数并获取结果。
- 支持 Webhook 或回调，执行结束后通知外部系统。

### REQ-021：权限与审计

第一版不实现登录、角色、权限和审计。若平台后续部署为多人共享环境，应再提供基础权限与审计能力。

建议能力：

- 用户登录。
- 设备占用者展示。
- 用例创建 / 修改人记录。
- 执行任务创建人记录。
- 管理员释放设备。
- 操作审计日志。

MVP 必须保留 `createdBy`、`updatedBy`、`lockedBy` 等扩展字段的设计空间，但字段可为空或使用默认本地用户。

### REQ-022：稳定性与容错

平台必须处理常见不稳定情况。

至少覆盖：

- 设备断连。
- 设备重连。
- 预览流中断。
- 控制命令超时。
- 测试执行中断。
- 后端服务重启。
- 浏览器页面刷新。
- 日志或截图写入失败。

用户可感知要求：

- 不能静默失败。
- 执行失败要有明确状态和原因。
- 中断时已采集的数据不能丢失。
- 报告应能标记未完成原因。

### REQ-023：安全与隐私

平台可能采集设备截图、日志和崩溃信息，因此必须考虑安全与隐私。

要求：

- 报告、截图、日志应存储在受控目录。
- 设备录屏视频应和其他 artifact 一样存储在受控目录，不应写入任意本机路径。
- 执行视频应和截图、日志、报告一起进入统一 artifact 保留策略，不按 Run 成败即时删除。
- 历史执行视频只能由显式清理策略、手动删除 Run 或空间保留策略清理。
- 不应在日志中打印密钥、Token、账号密码等敏感数据。
- 导出报告前应能识别或提示可能包含敏感信息。
- 若接入多人环境，需要权限控制。
- 若接入公网或远程访问，需要认证和访问控制。

### REQ-024：可扩展能力

平台应为后续能力扩展保留设计空间。

后续可能扩展：

- OCR 文本识别。
- 图像匹配定位。
- 控件树定位。
- 断言步骤。
- 条件分支。
- 循环步骤。
- 变量和参数化。
- 数据驱动测试。
- 脚本模式。
- 失败自动重试。
- 规则模板把常见自然语言期望转换为候选结构化断言。

### REQ-025：测试保障与回归防护

平台必须建立单元测试、集成测试和核心流程回归测试模块，避免功能迭代时破坏已验证能力。

测试保障范围：

- Step schema 校验。
- 坐标转换和横竖屏映射。
- ActionStep 编辑、排序、启用 / 禁用。
- Test Runner 状态机。
- 执行模式：一次、N 次、循环、暂停、继续、停止。
- 失败策略：停止、继续、重试。
- Device Driver 抽象和 Mock Driver。
- Android Driver 命令参数构造，不直接依赖真机。
- Metrics Collector 采样关联 run、iteration、step。
- DeviceEvent 异常事件关联 run、device、step。
- Report HTML 生成。
- Artifact 路径和清理策略。

质量门禁要求：

- 每次改动主功能逻辑前后都必须能运行测试命令。
- 新增核心逻辑必须同时新增对应测试。
- 修复 bug 时应增加回归测试，证明同类问题不会再次出现。
- 测试应优先覆盖纯逻辑和状态机，真实设备测试作为集成或手动验证补充。
- CI 接入前，本地必须提供一条统一测试命令。

### REQ-026：应用包管理

平台必须逐步从“只管理设备”升级为“同时管理设备和被测应用包”，并提供独立的 App 实体管理。

包管理对象包括：

- App：应用实体，包含显示名、平台、Android packageName 或 iOS bundleId。
- AppVersion / AppBuild：应用版本实体，建议由 `versionName + buildNumber + commitId` 唯一标识一次构建。
- Android APK，后续可扩展 AAB。
- iOS IPA。
- 包来源：SMB 路径、手动上传、本地路径、HTTP 下载 URL、CI artifact URL、CI Webhook、内部包服务。
- 包元数据：App ID、包名 / bundle id、版本名、versionCode / build number、commitId、分支、渠道、构建时间、上传时间、构建人、文件大小、校验值。
- 包测试历史：该包在哪些设备、哪些测试计划、哪些流程上执行过，结果如何。

包管理能力包括：

- 注册 App。
- 登记新 AppVersion / AppBuild。
- 查询包列表和包详情。
- 解析包基础信息。
- 通过 SMB 服务器拉取最新包：支持 SMB 目录模板，按文件名规则解析版本、分支、buildNumber 等信息。
- 通过 CI/CD Webhook `POST /api/builds` 推送构建产物信息，平台自动创建版本记录。
- 手动上传 APK / IPA。
- 下载或导入包文件到 `<DATA_DIR>/builds/`。
- 安装到指定设备或设备组。
- 卸载目标 App。
- 覆盖安装或安装前自动卸载旧版。
- 执行前清理 App 数据，按平台能力区分。
- 安装后校验设备上目标 App 版本与包记录一致。
- 包下载、解析、安装、卸载和版本校验过程必须有可观察状态，能展示当前阶段、进度、开始 / 结束时间和失败原因。
- Android APK 解析 packageName、versionCode、versionName、minSdk。
- iOS IPA 解析 Bundle ID、CFBundleVersion；安装能力依赖签名、UDID、信任状态和工具链。

MVP 建议先支持 Android APK 的 SMB 拉包 / 本地路径 / 上传和安装；iOS IPA 安装依赖签名、设备信任和工具链，作为后续能力接入。

### REQ-027：测试计划与流程编排

平台必须支持把测试流程组织成可复用的测试计划。

测试计划应包含：

- 计划名称。
- 测试类型：冒烟、回归、稳定性、性能、兼容性、探索。
- 目标平台。
- 目标 App 或包筛选规则。
- 设备或设备组。
- 关联流程集合。
- 执行顺序或随机策略。
- 执行次数、时长、失败策略。
- 性能采样配置。
- 通过标准和质量门禁。
- 通知策略。

冒烟套件是测试计划的一种特殊类型，最低要求：

- 冒烟套件绑定某个 App。
- 套件由多个测试用例 / Flow 组成，用例本身是原子单位，一个用例可被多个套件复用。
- 套件内用例可标记为 required，required 用例失败时整体冒烟失败。
- 支持通过条件：全部通过、允许 N 个失败、仅 required 用例必须通过。
- 支持执行设备配置：一台或多台标准设备。
- 支持随机化模式：关闭、用例顺序 shuffle、用例池 sampling。
- `shuffle` 只打乱用例 / Flow 顺序，不默认打乱单个用例内部步骤。
- `sampling` 从更大的用例池中随机抽取 N 条执行。
- 支持通知接收人或企业微信 Webhook 配置。

流程来源包括：

- 从设备操作录制生成。
- 在可视化编辑器中手动创建。
- 从 JSON / YAML Flow 导入。
- 后续由规则模板根据常见自然语言描述生成候选步骤或断言，并由用户确认。

流程能力要求：

- 一个流程可以复用于多个包。
- 一个流程可以声明适用平台、适用版本、必需设备能力。
- 流程应支持动作步骤和断言步骤混排。
- 流程执行前必须校验目标设备、目标包和流程能力是否匹配。

### REQ-028：结构化断言与结果验证

平台必须支持对“指定流程对应测试结果”进行结构化验证。

建议断言类型：

- `assert_app_alive`：目标 App 进程存活。
- `assert_no_crash`：执行区间内无 crash / ANR / hang。
- `assert_text`：OCR 识别屏幕指定矩形区域内的文字，与预期值按 contains / equals / not_contains 比对。
- `assert_image`：截取屏幕指定矩形区域，与人工审核过的基准图按相似度阈值对比。
- `assert_screen_changed`：操作后画面发生变化。
- `assert_metric_below`：性能指标低于阈值。
- `assert_metric_not_regressed`：性能指标相对基线未劣化。
- `assert_log_not_contains`：日志中不包含指定错误关键字。

验证要求：

- 断言步骤必须出现在步骤列表和报告中。
- 断言失败必须包含失败原因、截图、日志或指标证据。
- `assert_text` 应支持 region、expected、mode、ocrEngine 参数；OCR 引擎必须可替换，并优先支持本地 RapidOCR HTTP 服务、PaddleOCR HTTP 服务、Tesseract、macOS Vision fallback，不依赖外部云 API 或 token。
- `assert_image` 应支持 region、baselineArtifactId、threshold 参数。
- `assert_image` 第一次执行时生成“待审基准图”，不直接生效。
- 测试人员在报告中审核并点击“确认设为基准图”后，基准图才进入 approved 状态。
- UI 有意变化时，应支持手动更新基准图，旧基准图进入 superseded 状态。
- `assert_image` 失败时，报告必须展示实际截图、基准图、差异图并排对比。
- 自然语言期望结果优先通过规则模板解析为候选断言；无法解析时只作为备注，不能直接作为自动判定依据。
- 平台应允许用户为断言设置超时时间、重试次数和失败策略。

### REQ-029：新包冒烟自动化

平台应支持对新构建包发起冒烟验证。

冒烟流程建议包含：

- 包下载或导入。
- 包信息解析。
- 安装到目标设备。
- 启动 App。
- 检查版本一致。
- 执行固定关键流程。
- 采集 crash / ANR / hang / 命令失败。
- 采集轻量性能指标。
- 可选执行短时可控随机探索。
- 生成报告并通知。

触发方式包括：

- 人工在面板中选择包发起。
- CI/CD 或包服务 Webhook 触发：平台接收 `POST /api/builds`，按 App 和分支过滤规则自动选择冒烟套件。
- API / CLI 触发。
- 定时任务触发：支持 cron 表达式，例如每天凌晨对最新包跑一次巡检套件。

通过标准至少包括：

- 包可安装。
- App 可启动。
- 固定关键流程通过。
- 无 crash / ANR / hang。
- 无设备断连或关键命令失败。
- 当前阶段性能指标进入报告和并排对比，不默认作为自动失败条件；后续可开启阈值告警。

执行期间必须主动监听：

- Android `logcat` 中的 `FATAL EXCEPTION`。
- Android `logcat` 中的 `ANR in`。
- 目标 App 进程退出。
- 预览断流、设备断连、命令失败。

### REQ-030：性能基线记录与版本对比

平台必须按「App + 版本 + 设备 + 套件 / 用例」的粒度持久化记录每次执行的性能指标，并支持不同版本之间的性能数据并排对比展示。

性能基线维度：

- App。
- 包版本。
- 分支 / 渠道。
- 设备型号。
- 系统版本。
- 测试计划。
- 测试流程。

建议对比指标：

- App 启动耗时。
- 关键流程耗时。
- CPU 平均值 / 峰值。
- 内存平均值 / 峰值。
- FPS 平均值 / 最低值。
- 卡顿次数或长帧次数，平台支持时采集。
- 网络收发量。
- 电量和温度，平台支持时采集。
- crash / ANR / hang 数量。

对比策略：

- 报告详情页提供“与历史版本对比”入口。
- 用户选择基线版本；默认自动推荐同设备、同套件、最近一次通过版本。
- 包版本列表页支持选中两个版本点击“对比”。
- 对比表格并排展示两个版本所有指标，标注绝对变化值和百分比变化。
- 当前阶段不做自动劣化判定，不自动阻断流程，仅展示数据供人工判断。
- 后续可选支持指标阈值告警，例如 CPU 涨幅大于 15% 时推送企业微信预警。

### REQ-031：自动触发、调度与通知

平台应支持自动化测试任务的触发、调度和结果通知。

触发来源：

- 用户人工触发。
- CI / 包服务新包回调。
- 定时任务。
- 外部 API / CLI。
- 后续支持 MCP 或其他 Agent 工具接口触发。

调度要求：

- 根据设备组和设备锁选择可用设备。
- 支持排队、运行中、取消、失败、完成状态。
- 同一设备同一时间只能执行一个任务。
- 支持失败后重试或跳过。
- 支持任务超时。

通知要求：

- 支持 Webhook。
- MVP 优先接入企业微信 Markdown 消息。
- 通知接收目标可在套件或执行任务级别配置企业微信 Webhook URL，支持多个 URL。
- 通知内容应包含包信息、测试计划、总体结果、失败流程、失败步骤、异常摘要、版本性能摘要和 HTML 报告链接。
- 正常通过的通知可配置为静默、摘要或完整通知。

通知时机：

- 新包自动接入：检测到新包并自动发起冒烟。
- 冒烟测试完成且通过：推送包版本、设备信息、通过率和报告链接。
- 冒烟测试完成且失败：推送失败用例、崩溃 / ANR 摘要和报告链接。
- 手动执行测试套件完成：可配置是否推送。

CI/CD 集成要求：

- 提供 `POST /api/builds` 接口接收构建产物信息，包括 appId、version、buildNumber、branch、commitId、downloadUrl、triggerSmoke、smokeSuiteId、deviceIds。
- CI/CD 打包完成后通过该接口推送，平台自动处理包接入和冒烟触发。
- 响应应包含 buildId 和可选 runId，CI 可轮询执行状态。
- 外部工具接口必须复用平台已有 API、权限和任务队列，不允许绕过设备锁、包校验和报告生成。
- 所有通知、CI、SMB、MCP 或 Webhook 密钥都必须通过环境变量、部署配置或 Secret 注入，不得写死在代码、日志或报告中。

### REQ-032：可控随机探索与稳定性探索测试

平台应提供独立的稳定性探索测试能力，用于按起始方式进入目标 App 后持续探索可点击 / 可滑动位置，发现 crash、ANR、黑屏、卡死、跳出 App、未知页面和不可恢复状态。该能力类似 Monkey / Fastbot 的稳定性测试层，但必须受页面资产、视觉识别和安全策略约束；它不能替代 PageStateFlow 目标执行、StructuredFlow 回归流程或页面资产人工确认。

稳定性探索测试应支持三种策略：

- 资产引导探索：优先使用当前已识别 PageModel 上已保存的 PageElement / PageAbility，适合验证已录资产的覆盖和稳定性。
- 视觉候选探索：在没有已保存能力或需要扩大覆盖时，使用带区域约束的 OCR 文本、截图视觉候选和安全区域生成候选动作。
- 可控随机探索：在安全策略允许时，对非危险区域执行少量随机点击、滑动、返回或等待，用于发现未录入口和未知异常。

探索不应是无边界乱点，必须可控：

- 可配置最大时长。
- 可配置最大动作数。
- 可配置动作集合，例如点击、滑动、返回、输入。
- 支持探索策略，例如保守、平衡、激进。
- 支持黑名单区域、黑名单页面和危险文案黑名单，例如删除、退出登录、注销、支付、发布、提交、确认删除；危险词应支持按 packageName 保存补充项，同一包再次探索时自动回显。
- 支持随机种子，失败后可复现。
- 支持起始方式配置：启动目标 App、从当前页开始或重启目标 App；默认使用重启目标 App，确保每次探索从更干净的 App 进程状态开始；从当前页开始时必须校验当前前台包等于目标包，否则直接失败并记录 `start_state_failed`。
- 支持 App 外恢复策略：若探索过程中跳到桌面、系统页或其他 App，应按配置返回 App、重启 App 或停止；默认返回 App，降低因短暂跳出目标包导致整次探索被重启的概率。
- 支持 App 内回退策略：可配置不主动返回、浅层回退或深度优先回溯，并通过最大探索深度约束详情页、H5 页和叶子页停留范围；默认最大深度为 4。
- 支持 root 页面恢复策略：当当前页面无可执行候选或路径不可恢复时，可返回到主页 / 首页 Tab 等已配置根页面后继续探索。
- 探索过程中持续监听 crash / ANR / hang / 设备断连。
- 探索过程中持续检测黑屏、长时间无画面变化、App 退出、输入法遮挡导致的预览异常和未知页面。
- 动作执行后不得只依赖固定短等待；平台应在上限时间内轮询 Observation，识别 H5 / WebView / 网络加载态，等待页面脱离加载态并稳定后再进入下一轮候选选择。
- 当某个候选动作执行后页面无实质变化时，平台应在当前页面签名下跳过该候选，继续尝试其他安全候选，避免同页重复点击同一 OCR / 视觉目标。
- 当候选动作进入新页面并完成回退后，平台应在父页面跳过已覆盖入口，继续探索其它安全候选，避免同一入口反复进入 / 返回。
- 报告中记录探索路径、随机种子、每步截图、页面识别结果、动作来源、候选过滤原因、失败前步骤和证据。

探索结果治理要求：

- 稳定性探索测试必须作为独立入口展示，不能混在目标页面执行或正式回归用例执行结果中。
- 探索发现的新页面、新操作、新连接边只能进入 draft / candidate，不得直接写入 active PageMatcher、PageElement、PageTransition 或 PageTask。
- 用户确认后，候选资产仍必须通过资产录制、页面能力和连接边流程入库。
- 探索报告必须能导出可复现动作序列；当发生 crash / ANR / 黑屏 / App 退出时，必须保留日志、截图、视频时间点和 seed。
- 该能力排期在 PageStateFlow 核心目标执行稳定后进入开发，优先作为新包冒烟和稳定性巡检的补充层。

第一版稳定性探索范围：

- Dashboard 新增独立“稳定性探索”入口，用户选择设备并输入 / 选择目标 Android packageName 后启动。
- 平台按起始方式准备目标 App，并在目标 App 内按最大时长、最大动作数、seed、探索策略、允许动作、回退策略、最大深度和危险词黑名单持续探索。
- 执行过程中展示当前 run、进度、当前包、最近动作、动作来源、过滤候选数和最近步骤时间线。
- 探索运行复用统一 Run / Report 体系，报告展示稳定性探索配置、seed、动作进度、过滤候选、异常事件和步骤截图。
- 第一版候选来源支持临时页处理规则、回退动作、已保存 PageElement / PageAbility、OCR 文本、安全视觉区域和随机安全区域；候选选择会过滤系统栏、纯数字、时间日期、同页无效重复候选和已回退覆盖入口；候选资产一键转人工确认、真实多设备并发和自动缺陷提报后续增强。

### REQ-033：外部工具接口与 AI 仓库导航

平台应为后续 CI、CLI、MCP、AI Agent 和开发者工具预留标准外部工具接口，并维护 AI 可读的仓库导航。

外部工具接口能力包括：

- 查询 App、AppBuild、SmokeSuite、Run 和报告。
- 触发手动冒烟、指定包回归、定时任务启停。
- 查询任务队列状态、设备占用状态和报告链接。
- 发送或重发企业微信 / Webhook 通知。
- 取消正在排队或运行中的任务。
- 后续可提供 MCP Server，把常用平台操作暴露给 AI Agent 或内部工具。

外部工具接口要求：

- 不能绕过平台的设备锁、任务队列、包版本校验和报告生成。
- 返回结果必须包含稳定 ID，例如 buildId、runId、jobId、reportUrl。
- 失败时必须返回结构化错误码和可读错误描述。
- 敏感配置不得出现在工具 schema、日志、报告、仓库文件或前端页面中。

AI 仓库导航要求：

- 仓库可维护 `.ai/repo-profile.yml`，描述仓库定位、技术栈、模块职责、入口、构建命令和风险边界。
- 仓库可维护 `.ai/context-guide.md`，作为 AI / 新维护者阅读代码的导航。
- `.ai/` 只保存仓库导航和上下文指南，不复制完整需求正文。
- 正式需求、设计、任务、验收和追踪矩阵仍以 `docs/product/mobile-automation-platform/spec/` 为事实来源。

### REQ-034：步骤级预期输入、验证与语义化固定流程

平台必须支持为每个步骤配置可执行的预期结果，并在回放时验证每一步是否符合预期。状态感知回放、起始状态、状态锚点和语义动作是提升固定流程稳定性的辅助机制；坐标型 `tap`、`swipe`、`input_text` 继续作为基础能力和兜底能力保留。

问题背景：

- 自动化测试的核心不是“动作有没有下发”，而是“每一步执行后是否达到预期结果”。
- 纯坐标回放只能复现“当时的物理动作”，不能证明步骤执行后的页面、数据、App 状态或性能表现符合预期。
- 滑动从 A 到 B 后再次回放可能继续到 C 只是一个例子；更通用的问题是每一步都需要有可解释的预期输入、验证方式和失败证据。
- 新包冒烟、回归测试和性能基线依赖稳定的固定流程，必须同时保证流程能走到正确状态，并能验证每个关键步骤结果。

步骤预期输入要求：

- 每个步骤应允许配置 0 个或多个预期结果。
- 预期结果必须优先保存为结构化数据，而不是只保存自然语言。
- 录制时平台应自动采集每一步的 before / after 截图、基础健康状态、异常事件摘要和可选 OCR 文本快照，并基于这些证据生成候选预期。
- 自动生成预期应按可靠性分级：
  - P0：无 crash / ANR、App 可响应 / 存活，默认启用。
  - P1：执行前状态校验、屏幕发生变化，默认建议启用或按动作类型自动启用。
  - P2：OCR 文字预期、局部截图相似度，默认作为候选项，需要用户确认或平台达到高置信度后才启用。
  - P3：全屏截图像素级对比，不作为默认硬断言，仅可作为诊断证据或用户显式配置。
- 平台不得把低置信 OCR、动态区域截图、全屏像素差异等不稳定信号自动保存为必过条件。
- 平台应提供常用预期模板：
  - 看到指定文字。
  - 指定文字不存在。
  - 指定截图区域与基准图相似。
  - 页面 / 屏幕发生变化。
  - 目标 App 仍在前台或进程存活。
  - 当前步骤后无 crash / ANR / hang。
  - 指定日志关键字不存在。
  - 指标低于阈值，例如耗时、CPU、内存、FPS。
- 平台应允许用户从步骤 before / after 截图中圈选区域，生成图像或 OCR 预期。
- 平台应允许用户输入自然语言预期，但只能通过规则模板生成候选结构化预期，并且必须由用户确认后才用于自动判定。
- 无法结构化的自然语言只作为备注展示，不参与自动通过 / 失败判定。

步骤验证要求：

- Runner 执行每一步后，必须执行该步骤关联的预期验证。
- 每个验证结果必须记录 expected、actual、status、失败原因和证据 artifact。
- 验证状态至少包括 passed、failed、skipped、unsupported、pending_review。
- 同一步存在多个预期结果时，默认全部通过才算该步骤通过；后续可扩展 any / required / optional 组合策略。
- 平台不支持某类验证时，必须标记为 unsupported，并说明缺少的能力，例如 OCR 未安装、iOS 不支持当前指标、图像基准图未确认。
- 验证失败后的处理策略应可配置：停止 Run、继续后续步骤、重试当前步骤、等待后重试。
- 报告必须按步骤展示预期、实际、验证方式、状态、截图、日志、视频时间点和失败证据。

用例 / Flow 起始状态要求：

- 测试用例或 Flow 应支持配置起始策略：
  - `keep_current`：保持当前设备状态。
  - `go_home`：执行前回到系统首页。
  - `launch_app`：启动目标 App。
  - `restart_app`：关闭后重新启动目标 App。
  - `clear_data_and_launch`：清理目标 App 数据后启动，按平台能力支持。
  - `install_build_and_launch`：安装指定包版本后启动，依赖包管理能力。
- 起始策略必须记录到 RunConfig 和报告中。
- 起始策略失败时，Run 必须给出明确失败原因，不应继续盲目执行后续步骤。

步骤状态锚点要求：

- 每个关键步骤可以配置执行前状态锚点和执行后状态锚点。
- 状态锚点建议支持：
  - 文本锚点：屏幕指定区域 OCR 后包含目标文本。
  - 图像锚点：屏幕指定区域与人工确认的基准图或录制时截图片段匹配。
  - App 锚点：目标 App 进程存活、当前 package / bundle id、Android activity 或 iOS 前台应用状态。
  - 屏幕变化锚点：操作后屏幕相对操作前发生变化。
- 状态锚点是回放定位和恢复的依据；结构化断言仍是测试结论判定的依据。两者可以复用 OCR / 图像能力，但语义不同。
- 录制时应保存 before / after 截图、设备分辨率、方向、目标 App 和可选 OCR 文本快照，便于用户在保存用例时挑选锚点。

语义动作要求：

- 条件步骤 / 可选弹窗处理：
  - 平台应允许在固定流程中插入“条件执行”步骤，用于处理启动弹窗、权限提示、更新提示等可能出现也可能不出现的 UI。
  - 条件步骤必须先验证触发条件，例如 OCR 识别到指定文字；条件满足时执行动作，条件不满足时记录 `skipped` 并继续后续步骤。
  - 条件步骤的跳过不应被视为测试失败；但必须在 StepResult 和报告里展示期望、实际、截图证据、尝试次数和跳过原因。
  - 条件步骤必须有最大等待时间、轮询间隔和可解释目标，避免回放无限等待。
- `wait_until_visible`：等待目标文字、图像或 App 状态出现，直到超时。
- `tap_on_text`：通过 OCR 找到目标文本区域并点击。
- `tap_on_image`：通过图像锚点或人工圈选区域找到目标区域并点击；当前 Android 一期支持人工 `region` 换算中心点执行，图像相似检索后续增强。
- `scroll_until_visible`：按指定方向滑动，直到目标文字 / 图像 / 状态出现，或达到最大尝试次数。
- `scroll_until_visible` 在目标已经可见时必须可以跳过，不应继续滑动。
- 语义动作必须配置超时时间、最大尝试次数、失败策略和可解释目标。

回放执行要求：

- Runner 执行每一步前，应检查步骤前状态锚点；不匹配时按步骤策略恢复、等待、跳过或失败。
- Runner 执行语义动作后，应检查步骤后状态锚点；不满足时记录失败证据。
- 对幂等语义动作，若步骤目标在执行前已经满足，Runner 可以跳过动作并记录跳过原因。
- 对原始坐标动作，Runner 至少应记录当前截图和坐标上下文；若配置了状态锚点，则先检查锚点再执行。
- Runner 执行动作后必须执行步骤预期验证，验证结果决定该步骤是否真正通过。
- 报告必须展示状态检查结果、跳过原因、恢复尝试次数、步骤预期、实际结果、最终截图和失败原因。

与现有规划的关系：

- 本需求是 REQ-028 结构化断言在步骤级流程中的落地方式；结构化断言提供具体的验证类型，步骤预期定义用户如何输入和组合这些验证。
- 本需求不冲突于 REQ-029 新包冒烟；冒烟应优先使用带步骤预期的固定流程，减少只看“动作执行成功”导致的误判。
- 本需求不冲突于 REQ-032 可控随机探索；随机探索应从一个已确认的稳定状态开始，不能替代固定流程。
- 第一版不要求接入大模型，也不要求完整 Appium / XCTest 控件树定位；优先用起始状态、截图锚点、OCR 锚点和人工确认完成 Android 闭环。

### REQ-035：语义定位录制、目标转换与步骤修复

平台必须把录制生成的原始坐标动作逐步增强为可维护的语义目标动作。坐标动作仍作为 fallback 保留，但关键回归、冒烟和性能流程应优先使用元素、文字、图像 / 区域等可解释目标。

行业参考结论：

- Appium Inspector 的核心价值是通过 Source 树、Selected Element 和 Suggested Locators 辅助用户选择稳定元素定位，而不是只记录坐标。
- Kobiton 等云真机 / scriptless 平台会把手工 session 转成可复跑用例，并在元素跨设备失效时提供重新选择或 remediation。
- 主流平台的共同方向是“元素 / 文字 / 图像定位优先，坐标兜底，执行证据和修复能力闭环”。

目标类型要求：

- `element`：通过 UI 层级定位目标控件，候选字段包括 Android resource-id、content-desc、text、className、bounds；iOS 后续通过 WDA / Appium source 补齐 accessibility id、label、name、type、bounds。
- `text`：通过 OCR 定位屏幕文字，支持 contains / equals、区域限制、超时和轮询；适合按钮文字、标题、弹窗文字。
- `image`：通过已确认基准图或录制时圈选区域进行图像匹配，支持阈值和区域限制。
- `region`：用户手动在截图上圈选固定区域，作为 OCR、图像匹配或点击中心点的目标来源。
- `coordinate`：保留录制坐标和归一化坐标，用于不可识别区域、临时调试和 fallback。

录制增强要求：

- 录制每个 tap / long_press / swipe 时，平台必须保存坐标、归一化坐标、设备分辨率、方向、预览渲染区域和 before / after 截图。
- Android first 阶段，tap / long_press 录制后应尝试从 UIAutomator dump 中找到点击点命中的最小可点击控件，并生成元素目标候选。
- 若控件候选缺少稳定 id 或明显属于动态列表项，平台应降低候选可靠性，不默认转换。
- OCR 只在点击点附近或用户选择区域内生成短文本候选；低置信、过长、疑似动态内容不能默认启用。
- 图像 / 区域候选必须由用户确认后才进入正式用例；首次生成的基准图可进入 pending_review。
- 每个候选目标必须记录来源、置信度、生成原因、适用平台和 fallback 坐标。

步骤编辑要求：

- 步骤编辑器必须清晰区分：
  - 坐标点击。
  - 元素点击。
  - 文字点击。
  - 图像 / 区域点击。
  - 条件分支：看到文字则点击，否则跳过。
- `tap_if_text` 只能作为可选分支能力展示，不应放在普通步骤快捷按钮中误导用户。
- 用户可以把原始 `tap` 转换为 `tap_on_element`、`tap_on_text` 或 `tap_on_image`。
- 用户可以查看每种目标的可靠性提示和失败风险；坐标和区域中心只作为调试 / 修复证据，关键 PageStateFlow 动作不默认使用坐标 fallback。
- 用户可以在失败报告中进入步骤修复入口，基于失败截图重新选择元素、文字或区域目标。

回放要求：

- `tap_on_element` 执行时应先查找匹配元素，再点击元素中心或指定偏移；找不到时按 failurePolicy 处理。
- `tap_on_text` 执行时应 OCR 截图并点击匹配文本区域中心；找不到时记录 `semantic_target_not_found`。
- `tap_on_image` 执行时若携带人工确认的 `region`，必须先通过 OCR、crop hash/template、视觉候选或结构候选在当前截图中重定位目标；重定位成功后点击当前目标中心或安全点，失败时记录 `runtime_relocation_required` 和修复证据，不得默认点击记录区域中心。
- `tap_if_text` 命中时执行点击，未命中时 StepResult 为 skipped，不计入失败。
- 语义动作执行后仍必须执行步骤预期验证；语义定位成功不等同于测试结论通过。
- Android 自动化执行的长期主路径应逐步升级为语义 driver：优先通过 UIAutomator2 / Appium-compatible driver 或等价 device-side automation agent 定位元素、等待 UI idle、执行点击 / 输入 / 滑动；裸 `adb shell input` 只能作为基础设施能力、临时调试能力或 fallback。
- ADB 仍是 Android 设备管理底座，继续负责设备发现、安装卸载、启动关闭、日志、性能、截图 / 录屏兜底和 UI dump 等能力；但关键业务图谱边不得把“裸 ADB 坐标点击成功”当作测试成功。
- 图谱执行报告必须标记本次动作使用的驱动通道，例如 `uiautomator2`、`appium`、`adb_input`、`scrcpy_control`、`wda` 或 `mock`，并在使用 fallback 时记录原因。

分阶段范围：

- 第一阶段：整理 Dashboard 步骤 UI，把条件分支入口从普通步骤快捷按钮中收敛；支持 `tap_on_text` 和 `tap_if_text` 的清晰区分。
- 第二阶段：Android UIAutomator 元素候选、`tap_on_element`、目标候选确认和 fallback 坐标。
- 第三阶段：截图区域圈选、`tap_on_image`、失败报告中的步骤修复入口。
- 第四阶段：Android 执行 driver 从裸 ADB 坐标动作升级为 UIAutomator2 / Appium-compatible 语义执行通道，支持元素等待、UI idle、稳定点击和更可靠文本输入。
- 第五阶段：iOS WDA / Appium source 语义定位能力对齐。

### REQ-036：业务图谱模型与图谱资产管理

状态：frozen / experimental upper layer

平台必须保留 v2 业务图谱内核作为状态建模、语义动作、预期验证和候选资产治理的底层能力，但产品主线不再追求穷尽整个 App 的全局业务图谱。业务图谱应服务于 PageStateFlow、结构化录制用例、关键路径、异常清障和证据解释，而不是要求系统理解并覆盖所有 App 状态。

冻结范围：

- 全局 App 可达图、图谱版本发布、候选资产治理和节点 / 边自动晋级不再作为当前 P0 / P1 主线继续扩张。
- 当前新功能默认进入 REQ-041 StructuredFlow 主线；只有明确重新打开业务图谱方向时，才继续增加图谱上层能力。
- 可复用底层能力继续有效：StateMatcher、ActionPolicy、Observation、RuntimeOverlay、动态等待、Runtime Interceptor、报告证据和 TestRuleStep 转换。

业务图谱核心要求：

- 平台必须支持 `BusinessGraph`，表示某个 App、平台和版本范围下的业务导航图。
- `BusinessGraph` 必须绑定具体被测 App 标识，Android 至少包含 `targetApp.androidPackageName`，iOS 至少包含 `targetApp.iosBundleId`；`appId` 只作为平台内业务资产 ID，不能替代设备侧真实包名 / Bundle ID。
- 任何录制、探索、导入或扫描产生的图谱资产，必须先校验当前 Observation 属于该 `targetApp`；系统桌面、其他 App、系统设置或无法确认归属的页面不得写入目标 App 图谱。
- 图谱必须区分“图谱资产版本”和“被测包版本”：同一个 App 的不同包版本可以共享图谱，但节点 / 边 / matcher / expectation 应保存首见版本、最近验证版本、兼容版本范围和废弃版本信息。
- 平台必须支持 `BusinessNode`，表示可识别业务页面、业务位置或关键状态，例如首页、班级页、发布作业页、新建作业页。
- 平台必须支持 `OperationEdge`，表示从一个业务节点到另一个业务节点的可执行操作。
- 图谱底层必须是有向图，不应强制树形结构；树形只作为 UI 展示形式之一。
- 图谱只表达稳定业务结构，不应把弹窗、loading、权限框、网络错误、toast 等运行时扰动建为业务节点。
- 同一 Activity / 页面内的稳定浮层、Tab 态或业务位置可以建为 `business_state`，例如发布活动面板、教师班级列表等；这类节点必须有足够具体的组合 matcher，不能只依赖一个宽泛文本。
- 弹窗、权限、loading、网络错误等应进入 Runtime Interceptor、BlockingRule、RecoveryPolicy 或 ActionPolicy。
- 节点和边必须支持 draft、active、deprecated、rejected 等状态。
- active 图谱必须支持版本化，历史 Run 必须保存当次使用的图谱版本或 RoutePlan 快照。
- 图谱必须能和 App、AppBuild / AppVersion、TestSuite、Run、Report 关联。

业务节点要求：

- 节点必须保存稳定 ID、名称、平台范围、所属 App、标签、描述、维护状态和版本信息。
- 节点必须配置一个或多个 StateMatcher，用于判断当前设备是否处于该节点。
- StateMatcher 可包含 activity / route / fragment / view controller、resource-id、accessibility id、content-desc、文本、OCR 文本、截图区域、当前 package / bundle id、URL / deep link、自定义断言等。
- StateMatcher 必须支持权重和阈值，不能只靠单一 OCR 或单一坐标判断。
- 节点必须可配置默认进入预期，例如显示指定文案、关键元素可见、App alive、无 crash / ANR。
- 节点粒度应以“业务可识别状态”为主，不应把每个微小按钮点击都建为节点。

操作边要求：

- 边必须保存 fromNode、toNode、名称、动作意图、前置条件、动作策略、后置预期、失败策略、可靠性评分、来源和维护状态。
- 边的动作策略必须支持优先级列表，例如先 `tap_on_element`，再 `tap_on_text`，再 `tap_on_image`，最后坐标 fallback。
- 正式 active 图谱不得把坐标型 `tap`、`long_press`、`swipe` 作为主动作策略；坐标只能存在于 legacy 录制回放、临时调试或 fallback ActionPolicy 中。
- 图谱动作应优先使用确定性定位信息：Android resource-id / class / content-desc / text / image region，iOS accessibility id / label / view hierarchy / image region。
- 当宽泛页面节点和具体业务状态节点同时命中时，状态识别应优先证据更完整、更具体的节点，并在报告中展示候选分数、命中权重和 matcher 证据。
- 边的前置条件必须至少能表达当前状态是 fromNode、无阻塞弹窗、目标控件可见或可等待。
- 边的后置预期必须至少能表达状态迁移到 toNode、无 crash / ANR、App 可响应。
- 边必须记录来源：source_scan、exploration、manual_recording、manual_edit、imported、ai_draft。
- 从同一个 fromNode 到同一个 toNode 可以存在多条边，用于不同入口、不同角色、不同平台能力或不同稳定性策略。

图谱治理要求：

- 候选节点 / 边不得直接进入 active 图谱，必须经过运行时验证和置信度评估；达到自动晋级阈值的候选可以进入 active 图谱，低置信、冲突、高风险或无法验证的候选才进入人工治理队列。
- 平台必须支持候选节点 / 边合并，避免重复录制或扫描造成资产膨胀。
- 平台必须展示节点 / 边的最近执行次数、通过率、失败原因、最近失败报告。
- 平台必须支持废弃节点 / 边，但历史报告仍能解释当时使用的图谱版本。

### REQ-037：多来源业务图谱生成

状态：frozen / experimental upper layer

平台必须支持从源码扫描、自动探索、手工录制和手工维护生成候选业务图谱。平台应保持独立系统定位，不要求业务 App 修改源码或内置测试契约。

冻结范围：

- 源码扫描、自动探索、录制转全局图谱、候选自动验证和自动晋级保留为实验能力；不再作为当前产品默认交付路径。
- 后续如果需要从源码或探索为 StructuredFlow 推荐候选状态 / 动作 / 预期，应以辅助建议形式接入，不应要求用户维护全局图谱。
- 不应新增面向全局图谱治理的大型 UI / API，除非产品明确重新打开该方向。

源码扫描要求：

- 源码扫描必须是只读行为，不向业务仓库写入自动化契约或代码。
- 源码扫描必须支持 `SourceWorkspace`，一个被测 App 可以由主工程、本地子工程、includeBuild / submodule、远程源码仓库、二进制 artifact 和源码索引服务共同组成。
- 源码扫描必须区分源码可见性：本地源码目录可直接扫描；远程 AAR / framework / 二进制依赖只能提供 manifest、resources、R.txt、Info.plist、资源文件或有限字节码线索，不能保证还原高质量业务路径；如需全量跨仓源码，应通过通用源码索引服务或源码仓库 provider 补齐。
- Android first 阶段应支持扫描 AndroidManifest、Activity、Fragment、Navigation XML、Compose NavHost、Router / DeepLink、layout XML、strings、onClick、navigate、startActivity 等信息。
- iOS 阶段应支持扫描 Info.plist、SceneDelegate / AppDelegate、UIViewController、Storyboard / XIB、SwiftUI NavigationStack / NavigationLink、Coordinator / Router、URL scheme / universal link、localized strings、accessibilityIdentifier、label / title 等信息。
- 平台应支持可配置 `SourceProvider`，例如 `LocalSourceProvider`、`SourceIndexProvider`、`ArtifactProvider`；候选资产必须保留 provider、repo、branch、module、artifact、file、line 或 symbol 来源。
- 源码扫描应生成候选节点、候选 matcher、候选边、候选动作策略和候选预期。
- 源码扫描结果必须标记来源、置信度、文件路径、行号或可追溯来源，用于自动验证、审计和异常治理。
- 源码扫描不得把所有类、组件、按钮都无差别升级为业务节点，必须按业务可识别状态过滤。
- 源码扫描不应只支持 Android；UI 和 API 必须暴露平台范围，Android / iOS 使用同一候选资产模型，平台差异通过 scanner plugin 和 capability 标记体现。

自动验证和晋级要求：

- 候选资产导入后，平台应按可控策略在真机或模拟器上验证候选节点 / 边是否可识别、可达、可重复执行。
- 自动验证至少采集 before / after Observation、截图、UI tree 或 WDA source、OCR、日志、crash / ANR / hang、动作结果和耗时。
- 候选置信度必须综合源码信号、运行时通过率、matcher 稳定性、跨设备 / 跨版本稳定性、是否依赖 fallback、异常事件和证据完整度。
- 连续多次验证通过、无冲突、无异常且置信度达阈值的候选，可自动晋级为 active 或进入待发布版本；冲突、低置信、不可达、重复疑似、依赖动态文案或图像不稳定的候选进入异常治理队列。
- 人工治理应是异常路径，不应要求维护者逐条 review 所有扫描候选。

自动探索要求：

- 自动探索用于无源码 App、源码扫描覆盖不足或发现实际可达路径。
- 自动探索必须在设备上运行，采集 UI 树、OCR、截图、activity / bundle 状态、操作结果和异常事件。
- 自动探索必须有边界：最大时长、最大动作数、黑名单区域、停止条件、可重放 seed。
- 自动探索生成的节点 / 边默认是 draft，不能直接进入 active 图谱。
- 自动探索遇到 crash / ANR / 设备断连时必须停止或隔离，并保存证据。

手工录制要求：

- 手工录制不再直接等同于最终用例，而是生成候选节点、候选边、候选动作策略和候选预期。
- 录制时平台必须采集动作前后 Observation，并尝试识别 beforeNode 和 afterNode。
- 录制写入图谱时必须按 `beforeNode + action + afterNode + expectation` 结构合并到当前 App 图谱；如果 before / after 不是目标 App 或缺少有效状态信号，应跳过写入并展示原因，不能生成无意义未知节点。
- 录制结果必须保留原始线性路径，便于复现和回退，但长期应支持转成图谱路径。

手工维护要求：

- Dashboard 必须支持候选节点 / 边查看、确认、合并、废弃和补充预期。
- 第一版可以采用列表 + 详情，不强制实现复杂画布。
- 后续可增加拓扑视图、路径高亮和图谱 diff。

### REQ-038：目标节点路径规划与图谱执行引擎

状态：frozen / experimental upper layer

平台必须支持用户、CI 或 AI 输入目标节点，由平台自动识别当前状态、规划路径、执行路径并验证结果。

冻结范围：

- 目标节点路径规划、RoutePlanner、GraphRunner、GraphRun API / CLI / MCP 保留为实验能力和未来验证入口，不替代 StructuredFlowRunner。
- 当前 AI / CI 自动化入口应优先围绕 StructuredFlow：选择 Flow、可选执行到中间步骤、传入 RuntimeOverlay、获取结构化报告。
- Graph RoutePlan 若未来重新启用，必须先转换为同一 TestRuleStep 执行规则，不能复制 StructuredFlowRunner 的私有逻辑。

路径规划要求：

- 用户可以选择目标节点、目标边、目标路径或节点集合作为测试目标。
- 平台必须先识别当前业务节点；识别失败时按起始策略回到根节点，例如启动 App、重启 App、清数据启动或安装指定包后启动。
- 平台必须支持从当前节点或根节点规划到目标节点的路径。
- 真实执行必须采用两阶段规划：第一阶段采集 Observation 并识别当前位置；如果当前状态在目标 App 内且能匹配 active 图谱节点，则直接从当前节点规划；如果当前状态在 App 外、未知、阻塞或未登录等不可规划状态，则先执行 bootstrap / startStrategy，让设备回到可识别起点，再重新采集 Observation 并进入第二阶段规划。
- 当当前状态在目标 App 内、能稳定匹配 active 页面资产，但该页面到目标不可达时，平台应优先按受控恢复策略执行 `back` 一次或多次并重新识别页面；一旦回到可达页面，再从新的起点重新规划路径。该策略用于处理搜索页、临时详情页、二级页面等“当前可识别但不是目标路径起点”的状态，不要求用户为这些页面补齐到所有目标页的边。
- 起始策略必须可解释并进入报告，例如 launch_app、restart_app、clear_data_and_launch、install_and_launch、login_required、return_to_root；不能在未知状态下直接假定 root 已经成立。
- 自动 back 恢复必须有最大次数、适用条件和报告记录；未知页、低置信匹配、目标 App 外、登录态缺失或强阻断态不得盲目 back，应返回明确 route gap / start state failed 诊断。
- 第一版路径算法可以使用 BFS；后续支持权重和策略。
- 路径策略应预留：
  - `most_stable`：优先历史通过率高、可靠性评分高、fallback 少的边。
  - `shortest`：优先边数少。
  - `smoke`：优先标记为冒烟路径。
  - `performance`：优先耗时稳定、步骤少、性能基线可比的路径。
- 路径规划必须检测不可达、循环、缺失 matcher、缺失动作策略、平台能力不支持等问题。
- 路径规划必须检测图谱缺少目标 App 包绑定、坐标-only 动作策略等不可稳定复现问题，并将其作为阻断错误返回。
- 路径规划应优先选择 driver 通道更稳定的边；在其他条件接近时，优先级建议为元素级语义 driver、accessibility / WDA、OCR / image resolver、裸 ADB 坐标 fallback。
- 路径规划结果必须可展示、可确认、可写入报告。

图谱执行要求：

- Runner 执行 RoutePlan 时，应按边展开为可执行 RuleStep。
- ExecutionPlan 必须自动为每个 RuleStep 组装业务预期：前置条件由来源节点默认预期和边的 preconditions 组成；后置预期由边的 expectations 和目标节点默认预期组成。
- 每条边执行顺序必须是：等待 / 验证前置条件 -> 运行拦截器处理阻塞状态 -> 选择动作策略 -> 执行动作 -> 采集截图、日志、指标和事件 -> 验证状态迁移和后置预期 -> 写入证据。
- 动作执行成功不等于边成功；只有状态迁移和后置预期通过，边才算通过。
- 状态迁移验证必须采用动态等待窗口，而不是固定 sleep 后单次判断。动作执行后 Runner 应按边级 waitPolicy 持续采集 Observation，直到目标节点匹配、后置预期通过、超时、crash / ANR、阻塞态或偏离态出现。
- waitPolicy 至少应包含 timeoutMs、pollIntervalMs、stableSampleCount、loading / blocker 处理策略和最大重试 / 恢复次数；默认值由平台提供，边可以按业务特性覆盖。
- 每一步必须默认检查 no_crash、no_anr、app_alive / app_responsive。
- 可选启用性能基线守护，例如关键节点耗时、CPU、内存、FPS 不明显劣化。
- 如果当前状态偏离规划路径，Runner 必须按策略执行恢复、重试、回到根节点、重新规划或失败。
- 恢复和重试必须有最大次数和可解释失败原因，避免无限循环。
- 执行报告必须展示规划路径、实际路径、每个节点 / 边状态、失败阶段、expected / actual、截图、视频时间点、日志和性能数据。
- 图谱执行器必须把“动作意图”和“底层执行通道”解耦：ActionPolicy 表达点击哪个元素 / 文本 / 区域，DriverAdapter 决定使用 UIAutomator2、Appium、WDA、scrcpy control、ADB input 或 mock 实际执行。

运行时治理要求：

- 弹窗、权限框、升级提示、loading、网络错误等必须由 Runtime Interceptor / BlockingRule 处理，不进入业务主图。
- ActionPolicy 必须支持多策略和 fallback，并在报告中记录实际使用的策略。
- RecoveryPolicy 必须支持回到上一个合法节点、回到根节点、重新规划、跳过可选边或失败。

### REQ-039：动态预期覆盖与 AI / CI 验证接口

平台必须支持 AI Agent、CI 系统或外部工具在一次执行中传入动态预期覆盖，用于验证代码变更后的目标节点行为。动态预期默认只作用于本次 Run，不污染 active 图谱。

动态预期要求：

- RuntimeOverlay 必须可以覆盖目标节点、目标边或路径中指定节点 / 边的预期。
- RuntimeOverlay 必须支持结构化预期，例如 `text_visible`、`text_not_visible`、`element_visible`、`image_matches`、`state_is`、`no_crash`、`metric_below`、`performance_not_regressed`。
- RuntimeOverlay 可以包含自然语言备注，但自动判定必须依赖结构化预期。
- RuntimeOverlay 不得自动写入 active 图谱；后续是否提升为正式预期必须通过人工确认或明确治理策略。
- 动态预期执行结果必须在报告中和图谱默认预期区分展示。
- 如果执行开始时已经识别为目标节点，平台仍必须创建目标节点验证步骤，验证目标节点默认预期、RuntimeOverlay 和系统守卫；不得因为路径为空而直接判定通过。
- 状态预期应优先使用稳定 UI 元素锚点，例如 resource-id、accessibility/content-desc、className 和文本组合；OCR 文字和截图比对应作为补充或 fallback。

AI / CI 调用要求：

- 平台核心接口必须优先提供 REST API；CLI 和 MCP 作为适配层，不应成为唯一入口。
- MCP adapter 应暴露给 AI Agent 的工具包括 list_apps、list_graph_nodes、get_node_detail、trigger_node_test、get_run_status、get_report、get_failure_evidence。
- API / MCP / CLI 触发的测试必须复用同一任务队列、设备锁、包安装、图谱执行和报告生成能力。
- 调用方必须能传入 App、包版本或包路径、目标设备 / 设备组、targetNode、runtime expectations、性能守护选项和通知策略。
- 平台必须返回稳定 ID、状态、结构化失败原因、reportUrl、screenshots、videoUrl、logs 和 failureEvidence。
- 失败返回必须能让 AI 判断是路径失败、状态识别失败、动作策略失败、动态预期失败、crash / ANR、性能劣化还是设备 / 环境问题。

安全和治理要求：

- 外部调用不得绕过设备锁、权限、包校验和报告生成。
- 外部调用中的敏感路径、token、账号信息不得进入公开报告或日志。
- AI 生成的图谱、预期或动作策略必须默认标记为 draft / overlay，不自动成为正式资产。

### REQ-040：v1 录制回放兼容迁移与回归保护

平台从 v1 线性坐标录制回放升级到结构化录制用例时，必须采用核心能力优先的迁移策略。v2 图谱内核中的状态识别、语义定位、预期验证、Runtime Interceptor 和报告证据应作为结构化录制用例的底层能力；迁移期间保留既有入口、历史数据和用户可用性，但不得为了旧坐标脚本兼容而牺牲语义动作、状态预期和动态等待结构。

v1 兼容要求：

- 现有线性用例模型、用例库、`/api/runs` 执行入口和 HTML 报告必须继续可用。
- Android 设备实时预览和浏览器内操控必须保持当前体验，不应因 Graph Runner 引入额外延迟或事件丢失。
- 录制步骤、编辑步骤、保存用例、选择用例执行、执行中状态展示、执行视频、每步截图和报告链接必须作为兼容回归保护项。
- v1 步骤级预期、条件弹窗步骤、起始状态策略、语义动作 schema 可以被 v2 复用，但不得在 v2 未稳定前删除或强制迁移。
- v1 用例数据不得被自动改写为图谱资产；转换必须生成候选图谱资产，并保留原始线性用例。

v2 增量接入要求：

- v2 必须新增独立的 graph model、graph storage、graph API 和 graph runner，不应直接替换 v1 runner 的外部行为。
- 目标节点执行入口应优先使用新增 `/api/graph-runs`，不复用 `/api/runs` 的语义，避免调用方混淆。
- v2 Graph Runner 可以复用 Driver、Device Lock、Artifact、Report、Expectation Evaluator、CLI 的基础能力，但必须通过适配层调用。
- v2 报告可以复用 report-core，但必须区分 legacy run report 与 graph run report。
- 新增 Dashboard 图谱页面和目标节点执行入口时，应避免把录制页、用例库页、执行页的既有功能挤压或隐藏。

转换桥要求：

- 平台应提供 v1 用例到候选图谱路径的转换能力，转换结果默认 draft。
- 转换时每个 v1 step 应尽量生成 OperationEdge 的 ActionPolicy；原始坐标动作只能作为 fallback。
- 转换时应尝试用 step 前后 Observation 识别 beforeNode / afterNode；无法识别时生成待补充 matcher 的 CandidateNode。
- 转换结果必须保留 source case id、step id、截图、录制时间和原始参数，便于回溯。
- 图谱路径可以临时展开为 RuleStep / ActionStep 执行，但展开结果应作为 routePlanSnapshot 保存，避免历史报告依赖后续图谱变更。

质量门禁要求：

- 开始实现 T-060 前，必须有 v1 主流程回归测试或等价 Mock Driver 集成测试覆盖：设备列表、预览控制、录制保存、回放执行、视频截图报告。
- 每完成一个 v2 增量任务，都必须运行 v1 主流程回归测试，确认旧能力没有退化。
- 任何删除、替换、重命名 v1 API、数据表、UI 入口或报告字段的改动，都必须先在 tasks / acceptance 中明确迁移方案和兼容期。
- v2 入口默认不应成为 Dashboard 唯一入口；只有当图谱执行闭环、报告、回归测试和真实 Android 验证都通过后，才能考虑把主导航重心切到 v2。
- 录制回放迁移时，图谱内核优先级高于旧线性脚本结构。录制模块应逐步产出 before / action / after / expectation 形式的候选图谱资产，而不是要求 RoutePlanner、GraphRunner 或 StateDetector 为旧坐标步骤做结构性妥协。

### REQ-041：结构化录制用例与路径快照

结构化录制回放是 PageStateFlow 的线性路径快照能力。录制回放不应再只是坐标脚本，而应把每一步建模为“前置页面状态 + 语义动作 + 后置预期 + 异常修复 + 证据”的可复用测试流程。业务图谱能力降级为底层状态和规则能力，不再要求维护全 App 全局可达图谱。

结构化录制用例要求：

- 平台必须支持 `StructuredFlow` / Smart Recorded Flow，表示一条有限范围、可复用、可验证的测试流程。
- 每条用例必须绑定 App 标识和包版本信息，Android 至少包含 appName、packageName、versionName、versionCode；iOS 至少包含 appName、bundleId、CFBundleShortVersionString、CFBundleVersion。
- 用例命名默认规则至少包含：`App名-版本号-用例起点-用例终点-用户名称`；用户可编辑显示名，但系统必须保留结构化元数据。
- 每条用例必须保存起点状态、终点状态、账号 / 角色、录制设备、分辨率、方向、起始策略和兼容版本范围。
- 用例可以声明兼容包版本范围；超出范围时执行前必须提示风险或要求用户确认 / 显式覆盖。
- 用例库必须支持检索、筛选、执行、复制、编辑、禁用、版本历史和最近执行结果查看。

步骤结构要求：

- 每一步必须保存 beforeState、action、afterExpectation、systemGuards、artifacts 和 timing。
- beforeState 至少应包含当前 App package / bundle、activity / route / view controller、关键 resource-id / accessibility id、关键文本或 OCR、可选截图锚点。
- action 必须优先使用语义目标：`tap_on_element`、`tap_on_text`、`tap_on_image`、`input_text_to_element`、`scroll_until_visible`、`wait_until_state`、`back`、`home`、`launch_app`、`close_app`。
- 坐标只能作为 fallback 保存；正式回归用例中纯坐标步骤必须标记为低稳定性，并在执行前或保存时提示修复。
- afterExpectation 必须表达动作完成后的业务预期，例如进入某页面、出现某控件 / 文案、截图区域匹配、状态锚点成立、指标阈值满足。
- 每一步默认启用系统守护：无 crash、无 ANR、App 可响应；这些守护不需要用户每步手动配置。
- 每一步执行必须采用动态等待：执行动作后持续采集 Observation，直到后置预期满足、超时、异常、阻塞或偏离，而不是固定 sleep 后直接继续。
- StructuredFlow 和未来 BusinessGraph 必须共享同一套底层执行规则：`beforeState -> action -> afterExpectations -> systemGuards -> evidence`。BusinessGraph 可以在未来把 OperationEdge / ActionPolicy 转换成同样的规则步骤执行，但当前产品 UI、存储和用例库不应为了 BusinessGraph 过早复杂化。
- 底层规则步骤必须保留来源 metadata，例如来自手工录制、导入、图谱边、AI overlay 或手工编辑；报告应能展示本次执行使用的是结构化录制步骤还是未来图谱转换步骤。

异常修复要求：

- 权限弹窗、升级弹窗、公告弹窗、登录失效、网络错误、loading 卡住等运行时扰动应通过 Runtime Interceptor / BlockingRule 处理，不应塞进每条用例主流程步骤。
- Runtime Interceptor 必须有最大处理次数、命中证据、动作证据和报告记录，避免无限循环。
- 如果异常可修复，执行器应处理后继续等待当前步骤的后置预期；如果不可修复，必须停止或按策略失败，并生成可读证据。

用例复用与局部执行要求：

- 用户可以选择完整执行用例，也可以指定执行到某个中间步骤 / 中间状态即算完成。
- 用户可以从某一步开始执行，但执行前必须验证当前设备满足该步 beforeState；不满足时应提示需要先运行前置步骤或执行起始策略。
- 用户可以在执行前动态覆盖某一步或终点的预期，例如替换期望文案、添加图像基准、修改指标阈值；覆盖默认只作用于本次 Run，不自动污染原用例。
- 用例执行结果必须保存本次实际步骤、每步 expected / actual、截图、视频、日志、性能和异常证据。

MCP / AI / CI 调用要求：

- 平台必须提供 REST API 作为核心入口，CLI 和 MCP adapter 作为适配层。
- 外部工具必须能检索用例库、查询用例详情、触发用例执行、指定执行到中间步骤、传入 RuntimeOverlay、查询执行状态、获取报告和失败证据。
- AI 调用不应绕过设备锁、包版本校验、执行视频、截图、异常采集和报告生成。
- AI 动态修改的预期默认只作用于本次执行；是否保存回用例必须由用户确认或明确治理策略控制。

### REQ-042：PageStateFlow 页面状态资产主线

平台当前主线升级为 `PageStateFlow`。平台必须围绕 App 级页面资产库建设能力：识别当前页面、保存页面模板、提取可操作元素、沉淀动作结果、规划页面路径，并把录制回放改造成页面资产学习和路径快照执行。

主目标命名：

- 中文名称：页面状态资产驱动的移动端智能回放测试平台。
- 英文名称：PageStateFlow。
- 核心问题：平台应先稳定回答“当前在哪个页面、这个页面有哪些可操作元素、操作之后会发生什么”，再回答“如何执行一条回归流程或到达目标页面”。

页面资产要求：

- 平台必须支持 `PageStateLibrary`，按 App 管理页面资产；同一个 App 可同时绑定 Android packageName 和 iOS bundleId。
- 平台必须支持 `PageModel`，用于表达一个跨平台稳定逻辑页面或页面变体；弹层、菜单、黑条、Toast、权限框等不默认作为独立 PageModel 保存，而应作为页面内状态、条件步骤、Runtime Interceptor 或 PageTransition 结果维护。
- 每个 `PageModel` 必须拥有稳定逻辑 key，例如 `home`、`teacher_class_list`、`class_detail`；同一逻辑页面在 Android 和 iOS 上不得创建互不关联的两份主资产。
- 每个 `PageModel` 必须保存页面名称、页面类型、归属 App、逻辑 key、首见版本、最近验证版本、兼容版本范围、状态、创建来源和证据。
- 每个 `PageModel` 必须支持多个 `PlatformPageProfile`，分别保存 Android / iOS / mobile-both 的平台专属证据。
- Android profile 至少可保存 package、activity / route、resource-id、content-desc、class、UIAutomator dump、OCR 文本和截图区域；iOS profile 至少可保存 bundle、view controller / route、accessibility id、label、WDA source、OCR 文本和截图区域。
- 每个 profile 必须保存一组 `PageMatcher`，包括但不限于 package / bundle、activity / route / view controller、resource-id / accessibility id、content-desc / label、关键文本、OCR 文本、截图区域相似度。
- 平台必须支持跨端页面合并：当 Android 已有 `home` 页面，用户在 iOS 录入同样首页时，系统应通过逻辑 key、页面名称、通用 OCR 文本、截图区域相似度和人工确认提示匹配已有 PageModel，并更新该 PageModel 的 iOS profile，而不是默认创建新逻辑页面。
- 页面识别必须采用多信号加权匹配，不能只依赖单个 OCR 文本、单张截图或单个常见按钮文案。
- 页面截图必须支持用户圈选主要模块区域，区域匹配可作为页面识别和视觉回归的证据之一。
- 页面资产必须区分业务主页面、页面变体、阻断页和系统页面；权限、升级、公告、选择学科等临时阻断页应进入 Runtime Interceptor / BlockingPage，不应污染主流程页面路径。
- 菜单、弹窗、底部面板和局部浮动条默认不进入页面资产库。它们应沉淀在父页面的“页面能力”和“连接边”中，例如 `点击右上角加号 -> 等待菜单文字出现 -> 点击添加好友 -> 到达添加好友页`；如果只是局部状态变化，应保存为 PageTransition 的 local state / conditional step，而不是新建页面。
- 对于“上课中黑条”“同步状态条”“小范围悬浮提示”这类附着在父页面但父页面仍可正常操作的动态状态，录入页面时应通过圈选稳定区域、确认稳定 OCR / UI 文本来保证仍匹配父页面；动态账号名、班级名、时间、状态条文案等不应作为页面身份的强 matcher。
- 对于“创建公开课 / 创建班级 / 发布入口”等位于中间内容区且可能被滚动隐藏的入口，平台不得把它们作为 PageModel 的阻断型默认预期或唯一页面身份 matcher；它们应作为 PageElement / PageAbility 保存，并通过 `availability=after_scroll`、`scroll_candidate` 或滚动容器策略描述如何显露和点击。
- 页面信息必须支持编辑：用户可以修改页面名称、逻辑 key、版本兼容范围、matcher 权重、截图区域、元素 locator、转移预期和状态；编辑必须生成更新时间、来源和必要的历史记录，避免改版后旧信息静默失效。
- 页面资产必须支持版本失效治理：当新版本 App 页面改版导致 matcher 或 transition 连续失败时，平台应标记对应 profile / matcher / transition 为 `stale` 或 `needs_update`，并在执行报告和页面资产库中提示需要重新采集或编辑。
- 页面资产库必须支持删除无效资产；删除应优先实现为软删除 / 弃用状态，使资产从默认列表、目标搜索和路径规划中移除，同时保留历史报告、执行记录和旧转移引用的可追溯性。

AI 可理解资产要求：

- 每个 `PageModel` 必须保存 AI 可读字段：稳定 targetRef、中文名、英文 / 拼音别名、业务描述、页面用途、所属业务域、角色 / 权限、常见入口和意图标签。
- 每个 `PageElement` 必须保存 AI 可读字段：稳定 targetRef、显示名、动作意图、业务含义、可触发的 PageTransition 和风险说明。
- 每个 `PageTransition` 必须保存 AI 可读字段：自然语言摘要、前置页面、动作说明、目标页面 / 弹层、成功判定和失败提示。
- AI 可读字段不得只由底层 resource-id、activity 或坐标组成；必须能让外部 AI 在不知道业务代码的情况下理解“这个页面是做什么的、可以去哪里、怎么触发”。
- 页面资产库必须支持按 targetRef 精确查询，也支持按自然语言、别名、业务域、意图标签模糊检索。
- 当 AI 输入“去新建课堂页”“执行到班级详情”“点击发布活动”这类目标时，平台应返回候选 PageModel / PageElement / StructuredFlow，并给出匹配原因、置信度和需要用户或 AI 消歧的信息。
- 当候选目标不唯一时，平台不得直接执行；必须返回 disambiguation candidates，例如“新建课堂页-老师端”“新建课堂页-学生端”“课堂详情页”，并要求调用方选择 targetRef。
- 执行报告必须回显 AI 输入目标、解析到的 targetRef、候选消歧过程和最终执行路径，便于 AI 根据失败结果继续修复或补充指令。

页面元素要求：

- 平台必须支持 `PageElement`，用于表达某个页面上的可操作元素、区域或手势入口。
- `PageElement` 必须保存支持动作，例如 tap、long_press、swipe、input_text、scroll_until_visible、wait_until_visible。
- `PageElement` 必须保存多种 locator 候选，并按可靠性排序：resource-id / accessibility id 优先，其次 content-desc / label、文本、OCR 区域、图像区域，坐标只能作为 fallback。
- `PageElement` 的逻辑 key 应跨平台复用，例如 `primary_tab_teacher` 或 `create_lesson_button`；Android 和 iOS 的 locator 候选挂在各自 platform profile 下。
- 当多个元素拥有相同 resource-id、content-desc、label 或文本时，必须保存视觉序号、父子结构、邻近锚点或区域约束，不能只用坐标区分。
- 用户必须可以在面板上查看和编辑元素 locator 候选，并选择哪些候选作为强基准、建议基准或 fallback。

页面转移要求：

- 平台必须支持 `PageTransition`，用于表达在某个 PageModel 上执行某个 PageElement 动作后的结果。
- 转移结果必须支持五类 outcome：导航到目标页面、复合跳转到目标页面、打开页面内菜单 / 弹窗、局部页面状态变化、无可见变化但产生业务效果。
- 每条转移必须保存 source PageModel、action、target PageModel 或页面内状态描述、afterExpectation、系统守护、timing 和证据。页面内菜单 / 弹窗需要保存可等待条件、下一步动作和是否阻断当前动作，不作为独立目标页面参与路径规划。
- 对于“点击固定入口 -> 等待页面内菜单 / 弹层出现 -> 点击菜单项 -> 到达目标页”的场景，平台必须支持 `compound_navigation`，并保存可执行的 `compoundSteps`。例如 `点击主页右上角 + -> 等待添加好友文字 -> 点击添加好友 -> 到达添加好友页`，中间菜单不应保存成独立 PageModel。
- 对于动态列表 / 网格候选入口，平台必须支持 `grid_candidate` PageElement 和候选重试策略。若点击候选项进入详情页后，后续路径因为权限、角色或页面条件缺失失败，执行器应能返回候选源页并尝试下一个候选，同时在报告中说明失败原因和候选序号。
- 对于指定动态数据的候选入口，例如“进入某个名字的班级并创建课堂”，平台必须支持在 `grid_candidate.scrollProfile.targetQuery` 中保存运行期模板，例如 `{{className}}`，并允许目标执行通过 `RuntimeOverlay.runtimeParams` 注入 `className=班级四十一号`。执行器必须只在人工圈选的列表 / 网格区域内 OCR 查找该目标文本，必要时滑动该容器继续搜索；如果指定目标最终找不到或无法完成下游路径，必须报告参数化候选失败，不得自动切换为其它班级或第一个可见候选。
- 转移验证必须采用动态等待：动作后持续采集 Observation，直到目标页面 / 弹层 / 局部状态成立，或超时、阻塞、crash / ANR、设备异常。
- `screen_changed` 只能作为弱候选，不得替代“到达哪个页面 / 弹层 / 状态”的业务预期。

页面任务要求：

- 平台必须支持 `PageTask`，用于表达“已经到达某个 PageModel 之后，在该页面内部完成的一组任务步骤”，例如新建课堂页输入课堂标题、选择时间、勾选选项、进入次级编辑页、点击发布并等待成功提示。
- `PageTask` 默认不直接参与跨页面路径规划，不能替代 PageTransition。路径规划只负责到达目标 PageModel；到达目标页后，执行器再按目标动作选择的 PageTask 追加页内步骤。若一个 PageTask 本身就是源页面上的完整导航任务，例如“登录页输入手机号 / 密码 -> 勾选协议 -> 点击登录 -> 到达主页”，则必须仍保存为源 PageModel 的 PageTask，并由一条 PageTransition 引用该 `taskId` 作为 `source_page_navigation`，不得把多步输入和提交散落复制到连接边里。
- `PageTask` 的每个步骤必须引用当前 PageModel 已保存的 PageElement，或使用明确的 wait 步骤；不得把输入框、发布按钮、时长选择器等临时控件另存为新 PageModel。
- `PageTask` 一期必须支持 `text_input`、`tap`、`submit`、`wait`、`picker_select` 和 `toggle_set`。`text_input` 执行后必须截图 / OCR 反查输入结果，不能只以 ADB 命令成功作为通过；`picker_select` 必须支持 OCR 识别到 `45 分钟` 或 `45` + `分钟` 分裂框的选择器；`toggle_set` 在无法可靠判断当前状态且目标是关闭时必须安全跳过，避免误打开。`subpage_edit` 作为模型字段先保留，待次级页面 PageTask / subtask 执行策略补齐后再开放录入。
- 文本、班级名、课堂标题、手机号、搜索词等业务数据必须通过运行期参数传入，例如 `lessonName=数学课`，只能作用于本次 Run 的 ExecutionPlan 和报告 metadata，不得写回 PageModel / PageElement / PageTransition / PageTask，也不得成为页面身份 matcher。
- 页面任务执行报告必须展示 PageTask 名称、步骤名称、引用的 PageElement、使用的运行期参数 key、实际动作类型、执行结果和失败原因，避免只展示底层 action id。

录制与学习要求：

- 录制开始时，平台必须先识别当前 PageModel；无法识别但 Observation 信号充足时，应生成 draft PageModel，而不是保存“未知节点-未知未知”。
- 用户每执行一步，平台必须采集 before Observation、动作 locator 候选、after Observation，并生成或更新 PageTransition。
- 录制保存时，平台可以生成 StructuredFlow 作为线性路径快照；同时应把高置信页面、元素和转移写入 PageStateLibrary 的 draft 或 active 资产。
- 低置信、冲突、跨 App、系统页面或信号不足的候选不得自动进入 active；必须作为本次录制 evidence 或治理队列展示原因。
- 手工录制不应要求用户逐条维护全局图谱；UI 应优先展示“当前页面、动作元素、动作后页面 / 页面内状态、可执行预期”的结构。

路径规划与执行要求：

- 用户可以输入目标页面、目标元素动作或选择已保存 StructuredFlow 触发执行。
- AI / CI 可以输入稳定 targetRef，也可以输入自然语言目标；自然语言目标必须先经过目标解析和消歧，不能直接映射成隐式路径。
- 平台必须先识别当前页面；如果当前在目标 App 外，则按 startStrategy 启动 / 重启 / 安装并重新识别。
- 目标页面执行必须支持 `fast_visual` 快速执行模式：预检和执行阶段默认基于用户确认的截图重点区域、带区域约束的 OCR 依据和 `tap_on_image` / 人工区域动作执行；该模式不采集 UI tree，不依赖 UIAutomator / WDA source 作为主路径，并应复用预检阶段识别出的起点页面，避免 graph-run 启动后重复做一次起点识别。
- 当目标动作是内容区 `after_scroll` 能力时，执行器必须先用 OCR / 视觉依据确认目标是否当前可见；不可见时应执行受控滑动显露，再重新识别并点击目标，避免因为页面已滚动而直接点击旧录入坐标。
- 目标页面执行必须支持运行期参数输入，参数只作用于本次 Run 的执行计划和报告 metadata，不写回 PageModel / PageElement / PageTransition。业务数据如班级名、课程名、手机号、搜索关键字应通过运行期参数注入，不得沉淀为页面身份 matcher。
- 目标页面执行必须支持选择目标页已保存 PageTask 作为目标动作。执行时先通过 PageTransition 图到达目标 PageModel，再追加该 PageTask 的页内步骤；若目标页没有 PageTask，则只验证到达页面或执行 RuntimeOverlay 的目标验证。
- 快速执行模式可以继续使用 OCR，但应减少重复采集；如果一次 Observation 已满足页面匹配、路径预检或执行起点复用，不应为了同一阶段再次采集等价 OCR / screenshot / UI tree。
- 如果当前 PageModel 与目标之间存在已验证转移路径，平台应规划路径并展示每一步页面、动作和预期。
- 如果无法规划，平台应明确指出缺失哪类页面资产或转移资产，并提供“当前页面识别 / 录入”和“手工录制补齐路径”的入口。
- 执行报告必须展示规划路径、实际路径、每一步页面匹配分数、元素定位方式、expected / actual、截图、视频、日志、性能和 Runtime Interceptor 处理记录。
- PageStateFlow 执行报告必须结构化展示本步执行的 PageElement / action type / ability type / 候选序号、动作前后分别匹配到的 PageModel 和分数、复合 micro-step、重试 / 回退原因、失败原因，避免只展示 edge id 或底层 metadata。

Dashboard 产品形态要求：

- 平台必须保留现有“用例录制”和“用例库”模块；它们继续服务 StructuredFlow 路径快照、回归用例、问题复现和执行到中间步骤。
- 平台必须新增“资产录制”模块，专门用于录入和更新 PageStateFlow 页面资产。
- 资产录制模块一期采用人工录入形态：左侧为当前连接设备的实时预览和操作区，右侧为页面资产录入面板。
- 用户点击“开始录入 / 识别当前页面”后，平台采集当前页面的 screenshot、UI hierarchy / WDA source、OCR、activity / view controller、可操作元素、候选 matcher、候选 locator 和截图主区域候选，并在右侧展示给用户确认、编辑、保存或更新已有 PageModel。
- 页面资产保存 / 更新必须采用白名单确认模型：只有用户确认的 matcher、页面文字、OCR 文字，以及已经写入视觉 baseline artifact 的截图重点区域，才能生成正式 `StateMatcher` 并参与后续执行匹配；未确认候选、自动推断文本、平台控件噪声和无 baseline 的截图区域不得进入可执行 matcher。带 baseline 的截图重点区域应同时生成确定性 `image_region` 和轻量语义 `semantic_image_region`，前者用于强视觉基线，后者用 OCR tokens + layout + signature hash 提升动态内容下的召回；`image_region` 比较必须自动 mask 系统状态栏 / 系统导航栏重叠像素，并允许受控的小范围位置漂移。OpenCLIP / SigLIP embedding 只能作为后续可选增强。
- 如果一次保存 / 更新没有任何可执行确认依据，平台必须拒绝写入 active PageModel，并提示用户至少确认一个稳定依据或重新圈选可写入 baseline 的截图区域。
- 资产录制模块必须支持“更新已有页面”的流程：当当前页面与已有逻辑 PageModel 相似时，优先提示更新 Android / iOS profile，而不是新建页面。
- 资产录制模块应支持把用户操作一步沉淀为 PageTransition：展示动作前页面、动作元素、动作后页面 / 弹层 / 局部变化，并允许人工确认。
- 平台必须新增“目标执行”模块，专门用于输入目标页面 / 目标元素 / 可检索描述，并执行目标路径。
- 目标执行模块输入框必须支持 targetRef 精确输入、页面名 / 别名 / 业务描述 / 意图标签检索；输入时展示候选列表、平台覆盖情况、最近质量和匹配原因。
- 用户选择候选后，目标执行模块应展示从当前页面到目标的规划路径；确认后执行。
- 如果找不到候选，目标执行模块必须提示“尚未录入该页面资产”，并提供跳转到资产录制模块的入口。
- 如果找到目标但无法规划路径，目标执行模块必须展示 route gap，并提供跳转资产录制补齐页面或转移的入口。
- 平台必须新增“资产驱动巡检”模块或入口，和“自动探索 / 稳定性探索”明确区分。资产驱动巡检只消费已保存 PageStateFlow 资产，目标是验证页面资产、页面元素、连接边、页面任务和性能稳定性；自动探索 / 稳定性探索继续保留为发现未知页面、异常状态和 crash / ANR 的实验 / 补充入口。
- 自动探索录制作为二期能力规划，不进入一期默认闭环；它必须是“受控探索”：限定 App、限定最大步数、限定页面范围、限定危险动作黑名单，并把结果保存为 draft 页面 / 转移候选，不直接污染 active 资产。

跨平台要求：

- Android 原生、Compose、Flutter、iOS UIKit / SwiftUI 都必须通过统一 Observation 抽象进入 PageStateFlow。
- Android first 可以优先使用 UIAutomator dump、activity、resource-id、content-desc、OCR 和截图区域。
- 对于 PageStateFlow 目标执行，Android / iOS 都应优先走视觉页面识别和人工确认区域动作；UIAutomator dump / WDA source 保留为旧 StructuredFlow、调试、候选生成和 fallback，不再作为目标执行快速路径的默认依赖。
- iOS 后续使用 WDA source、view controller、accessibility id、label、OCR 和截图区域。
- Compose / Flutter 如果缺少稳定 accessibility / semantics 信息，平台必须降级为 OCR / 图像区域候选并提示稳定性风险。
- 如果一个逻辑页面只有 Android profile，没有 iOS profile，平台仍可在 iOS 上尝试使用 mobile-both 通用证据，例如主要截图区域、OCR 标题、通用页面描述和元素图像区域进行低置信识别 / 执行。
- 跨平台 fallback 必须显式标记为 `cross_platform_visual_fallback` 或等价原因，不能伪装成稳定 iOS 语义定位。
- 使用跨平台 fallback 成功或失败都必须进入报告；成功时提示建议补录 iOS 精确 profile，失败时提示缺失的 iOS matcher、locator 或 transition。
- 如果用户在 iOS 上补充了精确信息，平台必须把它合并到同一逻辑 PageModel 的 iOS profile，并优先使用 iOS profile 替代跨平台 fallback。

与现有能力关系：

- StructuredFlow 是 PageStateFlow 的线性路径快照，不再是唯一长期资产。
- BusinessGraph 上层继续保持 experimental / frozen；PageStateFlow 可以复用其 StateMatcher、ActionPolicy、Observation、RuntimeOverlay 和动态等待能力，但不继承“穷尽全业务状态”的目标。
- Legacy 坐标脚本只作为兼容和调试能力；新资产不得把坐标作为主定位策略。

### REQ-043：自动缺陷提报与 TAPD 集成

平台后续必须支持把自动化测试过程中发现的高价值问题沉淀为缺陷候选，并在配置允许时对接 TAPD 自动或半自动提 Bug。该能力属于报告、通知和外部系统集成层，不改变 PageStateFlow、StructuredFlow 或测试执行器的核心判定逻辑。

触发范围：

- 当 Run 发生 crash、ANR、设备断连、App 无响应、步骤预期失败、PageStateFlow 路径执行失败、视觉差异失败、性能阈值劣化或连续 flaky 失败时，平台应生成 `DefectCandidate`。
- 缺陷候选必须来源于已完成或已失败的执行证据，不允许在没有报告、截图、日志或步骤上下文的情况下直接创建 TAPD 缺陷。
- `passed` Run 默认不生成缺陷候选；如果存在非阻断 warning，例如性能轻微劣化或跨平台 fallback 风险，可生成低优先级候选但不得自动提交。
- TAPD 提报失败不得改变 Run 的测试结果；Run 是否通过只由测试执行和预期验证决定。

缺陷候选要求：

- 缺陷候选必须保存 appId / packageName / bundleId、App 版本、buildId、平台、设备、OS、测试入口、用例 / Flow / targetRef、失败步骤、失败阶段、错误码、expected / actual、日志摘要、截图 / 视频 / 报告链接。
- 缺陷候选必须保存可读复现步骤：StructuredFlow 步骤、PageStateFlow PathPlan、用户 / AI 输入目标、实际路径和失败点。
- crash / ANR 必须尽量附带 stack trace、ANR trace、logcat / syslog 摘要和进程信息；采集失败时必须说明缺失原因。
- 视觉差异或页面匹配失败必须附带实际截图、基准图 / 圈选区域、差异图或匹配分数。
- 性能劣化必须附带指标名、当前值、基线值、阈值和设备 / App 版本上下文。

去重和防刷要求：

- 平台必须为缺陷候选生成稳定 `DefectFingerprint`，至少由 app、版本范围、平台、设备族、测试入口、失败步骤 / 页面、错误码、失败阶段、stack / log signature、失败预期和关键截图 hash 组成。
- 相同 fingerprint 的失败不得反复创建新 TAPD 缺陷；应复用已有缺陷、追加运行证据、标记 duplicate candidate 或进入人工确认。
- 去重策略必须允许配置窗口，例如同一 App 版本内去重、跨 patch 版本去重、同设备族去重或全平台去重。
- flaky 失败必须达到配置阈值后才允许自动提报，例如同一 fingerprint 连续失败 N 次或在 M 次重试中失败率超过阈值。

提报策略：

- 平台必须支持 `disabled`、`manual_review`、`auto_create` 三种提报模式。
- MVP 默认必须是 `manual_review`：系统生成缺陷候选，用户在 Dashboard 报告详情或缺陷队列中确认后才创建 TAPD 缺陷。
- `auto_create` 只允许用于高置信失败，例如 crash / ANR、有稳定 stack signature、关键路径阻断、连续复现失败或显式配置的 CI 计划。
- 用户必须能够忽略候选、标记重复、关联已有 TAPD 缺陷、更新已有缺陷或提交新缺陷。
- 系统必须记录每次提交、忽略、关联、失败重试和自动判断原因。

TAPD 字段映射要求：

- TAPD 配置必须至少包含 workspaceId、缺陷模板 / 类型、默认模块、默认处理人、优先级 / 严重级别映射、标签、版本字段、自定义字段映射和提报策略。
- 缺陷标题应包含 App、平台、版本、失败类型和关键业务位置，例如 `[Android][ClassIn 6.0.1] 新建课堂页点击发布活动后崩溃`。
- 缺陷描述必须包含复现路径、预期结果、实际结果、设备信息、App 版本、报告链接、截图 / 视频 / 日志附件、fingerprint 和自动化运行 ID。
- TAPD 附件可以使用直接上传或报告 artifact 链接；如果附件上传失败，缺陷描述必须保留可访问报告链接。
- TAPD token、账号、签名或 API 密钥只能从环境变量、部署密钥或服务器安全配置读取，不能明文保存在 Dashboard、本地用例、MCP 参数或报告 JSON 中。

Dashboard 与外部调用要求：

- 报告详情页必须展示缺陷提报状态：未生成候选、候选待审核、已忽略、已关联、已提交、提交失败、重复候选。
- 报告详情页必须展示 TAPD 缺陷 ID 和可点击链接。
- 平台应提供缺陷候选队列，支持按 App、版本、失败类型、fingerprint、状态和最近出现时间筛选。
- REST / CLI / MCP 必须能查询缺陷候选、提交候选、关联已有缺陷和查询 TAPD 提报结果，但不得绕过权限、去重和提报策略。
- 外部 AI / CI 调用执行后，应能获取“本次是否生成缺陷候选、是否已提 TAPD、TAPD 链接、失败证据摘要”的结构化结果。

### REQ-044：资产驱动巡检

平台必须支持基于已保存 PageStateFlow 资产的巡检模式，用于稳定、自动地验证 App 关键页面、页面元素、连接边、页面任务和运行时质量。该能力不替代目标执行，也不删除现有自动探索 / 稳定性探索；它是介于“固定目标任务”和“盲目探索”之间的资产健康检查与主流程覆盖机制。

产品边界：

- 资产驱动巡检必须只以 active PageModel、PageElement、PageTransition、PageTask 和人工确认的页面区域为主要执行依据。
- 资产驱动巡检不得把所有 OCR 文本、UI dump 控件或截图候选都当成可点击目标；未确认候选只能进入建议或候选管理。
- 旧的自动探索 / 稳定性探索继续保留：它们用于发现未知页面、异常状态、crash、ANR、黑屏、卡死和 App 外跳转；资产驱动巡检用于验证“我们已经录入的东西是否还稳定”。
- 巡检入口应支持从当前设备当前页面开始，不强制重启 App；也应支持从指定根页面、指定页面集合或目标 App 启动后开始。
- 如果当前页面无法稳定匹配已保存 PageModel，巡检必须停止或进入只读诊断，不得继续盲点执行。

巡检计划要求：

- 平台应根据当前 PageModel 生成 `AssetPatrolPlan`，包含页面健康检查、区域滚动检查、元素重定位检查、连接边验证、PageTask 轻量执行和异常 / 性能守护。
- 页面健康检查至少包含：页面 matcher 是否命中、关键截图区域是否仍相似、关键 OCR 是否仍在预期语义区域内、动态区域 mask 是否仍有效。
- 区域滚动检查只允许在用户标注为内容区 / 列表区 / 动态区域的范围内执行，不得滑动标题栏、底部导航、系统栏或危险操作区域。
- 元素检查必须先通过语义 / 视觉 / 结构重定位找到 PageElement；如果只能依赖历史 `region_center`，必须记录为失败或需修复，不得点击。
- 连接边验证应按 PageTransition 的风险等级、最近失败率、业务优先级和巡检预算排序；高风险动作如删除、支付、发布、提交、退出登录、确认等默认跳过，除非测试计划显式允许。
- 对 `grid_candidate` / `scroll_candidate`，巡检可以执行安全的可见性 / 重定位检查；是否真正点击候选项应由策略控制，指定业务数据必须来自运行期参数。
- PageTask 巡检默认只执行 dry-run / 轻量验证，例如验证必填元素可重定位、参数可解析、提交前步骤可达；真正提交业务数据必须由显式测试计划允许。

报告与闭环要求：

- 巡检报告必须展示页面覆盖率、元素重定位成功率、连接边成功率、PageTask 可执行性、跳过原因、失败原因、耗时、crash / ANR / 黑屏 / App 外事件和性能采样。
- 每个失败项必须关联到具体 PageModel / PageElement / PageTransition / PageTask，并提供跳转到资产录制或失败修复 UI 的入口。
- 巡检发现的新页面、新元素、新边和疑似页面变体默认必须进入候选管理 / 资产录制确认流程；普通巡检不得自动写入 active 页面资产。若失败修复建议来自 REQ-045 的 AI 诊断，且满足高置信、低风险、验证通过和自动修复策略，则可以通过受控 AssetPatch 流程自动应用为新的 active 资产版本。
- 巡检结果应支持按页面、区域、能力类型、边、失败类型、设备、App 版本聚合，便于判断是 App 改版、资产过期、定位规则不足还是设备 / 环境问题。
- 巡检可以作为新包冒烟和定时任务的一部分运行，但不应替代核心目标任务；核心业务链路仍应通过目标执行或 StructuredFlow / PageTask 明确验证。

### REQ-045：探索异常 AI 诊断与受控资产修复

平台必须在自动探索、稳定性探索、资产驱动巡检和目标执行中提供统一的 AI 诊断闭环。当执行过程出现异常时，系统应先固化证据，再把结构化上下文交给 AI 判断异常类型，并根据策略决定报告、重启继续、生成缺陷候选、生成资产修复草稿或自动应用已验证的受控资产修复。

异常分类要求：

- 崩溃、ANR、黑屏、App 退出、系统弹窗阻断、性能阈值劣化、业务断言失败等必须优先归类为运行 / 业务异常，不得直接当作资产问题自动修复。
- 页面资产匹配不到、页面低置信、多候选、找不到连接边、PageElement 重定位失败、PageTransition 目标不达、PageTask 参数缺失等可以进入资产 / 测试计划诊断分支。
- AI 诊断必须返回结构化结论，至少包含 `classification`、`confidence`、`reason`、`evidenceRefs`、`recommendedAction` 和可选的资产修复建议。
- 当证据不足或 AI 低置信时，系统必须标记 `needs_human_review`，不能自动点击未知目标或直接改 active 资产。

证据要求：

- 发给 AI 前必须生成不可变的 `AiDiagnosisEvidencePack`，包含 runId、stepId、设备 / App / 版本、seed、最近动作序列、当前和前后 Observation、截图、OCR 文本、页面匹配诊断、元素定位诊断、连接边 / 任务上下文、性能采样、崩溃 / ANR / logcat 摘要和已有页面资产摘要。
- 证据包必须做敏感信息脱敏，例如手机号、密码、token、cookie、鉴权头和输入参数密文。
- UI tree、resource-id、accessibility-id、package/activity 等平台字段只能作为 debug evidence，不能被 AI 写成正式 PageStateFlow 便携匹配规则。

处置要求：

- 如果 AI 判断为 App / 业务异常，平台必须固化截图、日志、性能、复现步骤和诊断结果，生成缺陷候选或报告异常，并按策略重启 App / 回到起点 / 开始新的自动化分支。
- 如果 AI 判断为资产问题，平台应先生成 `AssetPatchCandidate`，例如新增 OCR 别名、更新截图重点区域、补充动态 mask、补充 PageElement 定位证据、创建 PageTransition candidate 或标记旧资产失效；默认进入 draft，只有当策略开启自动修复、AI 高置信、patch 类型低风险、证据完整且系统验证通过时，才允许通过受控接口自动生成新的 active 资产版本并继续本次执行。
- 资产修复 patch 必须通过系统验证，例如重新执行页面匹配、元素重定位或连接边轻量验证；验证失败、低置信、高风险或预算耗尽时必须保持 draft 并进入人工复核。
- 自动应用资产修复不得覆盖原始失败事实，必须记录 diagnosisId、patchId、旧版本、新版本、验证结果、应用策略、回滚入口和继续执行结果。
- AI 不得直接控制设备执行动作；设备动作仍必须由 Runner 根据验证后的 PageStateFlow 资产和策略执行。
- 系统必须提供受控 MCP / REST 工具给 AI 查询证据、查询资产、提交修复 patch、验证 patch、按策略自动应用已验证 patch、回滚 patch、创建缺陷候选和请求继续探索，但工具不得绕过设备锁、运行队列、证据存储、资产质量校验、风险策略、预算和人工审核策略。

## 非功能需求

### 性能

- 设备预览延迟应尽量低，MVP 目标建议小于 1000ms，最终目标小于 300ms，具体需按方案验证。
- 单步操作下发后，UI 应在 500ms 内展示命令状态变化。
- 性能采样不应显著影响设备测试结果。
- 报告详情页应能流畅打开包含数百步、数小时性能数据的执行记录。

### 可用性

- 录制和执行入口必须明显。
- 步骤编辑必须支持键盘或快捷操作的扩展空间。
- 对失败步骤、异常指标和崩溃信息应有醒目标记。
- 不支持的设备能力需要明确展示，而不是隐藏失败。

### 可靠性

- 执行过程中的每一步结果需要落库或持久化，避免任务中断后完全丢失。
- 设备断连后应尽快停止对该设备下发命令。
- 后端应能清理僵尸任务和失效设备锁。

### 可维护性

- Android / iOS 驱动层必须和业务层解耦。
- Step 模型必须稳定，避免每新增一个动作都改动大量模块。
- 报告生成应基于执行原始数据，不应只依赖 UI 状态。

### 可观测性

- 后端应记录关键服务日志。
- 执行任务应有唯一 Run ID。
- 设备命令应有 Command ID，便于追踪。
- 每个异常应有 Issue ID 或事件 ID。

### 测试保障

- 共享模型、坐标转换、Runner、报告生成等核心逻辑应具备单元测试。
- 后端 API、Recorder、Runner、Report Service 应具备 Mock Driver 集成测试。
- Dashboard 关键组件应具备组件测试或端到端测试。
- 测试命令应纳入开发流程，作为后续 CI 的基础。

## 边界和非目标

当前 Spec 不要求：

- 立即实现完整 Appium / XCTest / UIAutomator 控件级自动化框架。
- 立即把所有 Android 动作迁移到 UiAutomator2 / Appium；当前规划要求先建立 driver 通道抽象和 fallback 记录，再分阶段替换关键图谱路径。
- 立即实现 iOS 设备预览、控制、录制和回放。
- 立即支持云真机租赁或远程设备农场。
- 立即支持完整复杂脚本语言。
- 立即支持完全自由文本生成用例。
- 立即支持跨设备联动场景。
- 立即支持登录、角色、权限和审计。
- 立即支持所有性能指标，具体按平台和工具可采集能力逐步落地。
- 立即支持完整包管理平台、自动包下载服务和大规模设备农场。
- 立即支持无边界随机探索测试。
- 立即穷尽整个 App 的全部页面、全部异常状态和全部业务分支；PageStateFlow 只要求按关键路径逐步沉淀可验证页面资产。
